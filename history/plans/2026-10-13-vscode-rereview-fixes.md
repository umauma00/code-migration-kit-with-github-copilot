# VS Code改善の再レビュー4件：修正方針

対象は `feat/github-copilot-migration-kit` の未コミット差分。
[当初の実装方針](2026-10-13-vscode-orchestration.md)に追加する修正仕様。
親が方針と受け入れ条件を定め、GPT-6.1 Solが実装し、親が再レビューする。

## 1. 対象と維持する条件

今回の対象は、再レビューで再現したR1〜R4だけとする。
主な変更先は `lib/pipeline.mjs`、`lib/status.mjs`、関連テストと説明文書。
既存の未コミット変更は保持し、コミット・push・公開は行わない。

- runtimeのoriginal/mutation/parityと承認条件を維持する。
- source-onlyの独立2レビュー、build/smoke、handoffと「動作同等性未検証」を維持する。
- 出力を書くのは調整役だけとし、入力・出力・レビュー記録の変更検出を弱めない。
- 呼び出し上限、同時実行上限、修正回数、成功した片方のレビューを再利用する再開を維持する。
- 言語別テンプレート、モデル配分・費用管理、新しいpause/resume操作は追加しない。

修正前の全体テストは129件成功している。これを維持したうえで、今回の異常系と表示の
分岐を追加する。既存の失敗を隠すためにアサーションを弱めない。

## 2. R1：開始済みワーカーを回収するまでロックを保持する（P1）

### 再現と原因

独立したA・Bを並列実行し、Bのワーカーを保留する。Aが完了した直後にRULEBOOKを
削除すると、次の着手判断の `contextHash()` が例外を投げる。
現在はその例外がスケジューラーの外へ抜け、Bが実行中でもロックを解除する。
この経路ではrun summaryも残らない。変更前はBの終了を待ち、summaryを残していた。

### 実装方針

1. ロック取得から返却までを実行全体の寿命とし、その内側で開始したすべての
   `work()` Promiseを保持する。スケジューラーの例外も通常の失敗として記録する。
2. 入力ハッシュの不一致と、入力欠落・不正JSON等でハッシュを計算できない場合を
   同じ「新しい仕事を開始できない」経路へ集約する。元の原因と対象を残す。
   `done()` 等の確認処理が例外になった場合も、開始済みの仕事を取り残さない。
3. 致命的な入力・スケジューラー障害を検出したら、新規単位と待機中の未開始呼び出しを
   止める。既に開始したPromiseは全件settleするまでawaitする。
   単に `finally` でロックを外すだけの終了経路を残さない。
4. 入力が壊れてnative提出不能になる場合などは、内部AbortControllerと利用者のsignalを
   合成し、実行中アダプター・コマンドにも既存のキャンセルを伝えたうえで回収する。
   signalを受けても直ちに終了しないアダプターがある場合も、ロックを先に外さない。
   新しい利用者向け停止機能やタイムアウト設定は不要。
5. 呼び出し上限と通常のワーカー障害は、致命的な入力障害と区別する。
   上限に達する前に予約したレビュー、既に実行中で有効な独立レビューの回収を壊さない。
   キャンセル・変更後の入力に対する応答を成功記録にしない。
6. 記録先が書ける場合は、失敗原因・呼び出し件数・完了数をsummaryに保存する。
   残処理の回収と記録の後にロックを解放し、呼び出し元へ失敗を返す。
   エラー報告用の再集計が失敗しても、最初の原因を一般的なエラーに置き換えない。

初期検証中など、まだワーカーを開始していない失敗は従来どおり即時に終了してよい。
開始済み処理のない空キューで不要な入力再検査を繰り返さない。

### 受け入れ条件

- 保留中Bが残る間はrun Promiseが未完了で、ロックが残り、別の実行を開始できない。
- Bを終了させると全処理が回収され、ロックが解放され、summaryに元の入力障害が残る。
- 待機中Cのアダプターは呼ばれず、破損後のBの応答は完了として受理されない。
- 必須ファイル欠落だけでなく、依存宣言の不正JSONでも同じ終了経路になる。
- 回収後に遅れたstate書き込みが起こらないことを、保留アダプターを使って確認する。
- nativeのキャンセル・古い結果の拒否、通常の中断再開、片方だけ成功したレビューの
  再利用に関する既存テストを維持する。

## 3. R2：循環依存の判定と修正対象の選択を分ける（P2）

### 再現と原因

単位typecheckを無効にしたA↔Bの循環で、両候補を作成した後に呼び出し上限で止める。
`repair --target A` はpendingがAだけになるため、Bとの循環を認識できず、Bの完了を
待つ依存として残す。結果、ワーカー呼び出し0件で修正が拒否される。

### 実装方針

1. 監査した依存宣言から、manifest全体を対象に単位間の推移的依存と循環成分を求める。
   既存の推移的閉包による相互到達判定、または明確なSCC処理を利用してよい。
2. 実際に起動するキューは従来どおりpendingに限定し、repairでは指定単位だけとする。
   グラフの解析範囲が広がっても、利用者が指定していない単位を修正しない。
3. typecheckがnullの場合、同じ循環成分の内部だけ順序制約を外す。
   循環外の上流単位については、完了が必要な依存条件を維持する。
   manifest外の資料は固定ソースとして扱い、存在しない変換ジョブを待たない。
4. 単位typecheck付きの循環は、既存の具体的な診断で拒否する。
   今回の仕事に関係しない完了済みの別成分だけを理由に、独立した修正を拒否しない。

### 受け入れ条件

- 両候補が未完了のA↔Bでrepair Aが進み、Aに独立2レビューの有効な完了記録ができる。
- Bは呼び出されず、Bの出力・単位stateは変更されない。Aの修正をBの完了と扱わない。
- 循環外の未完了Cに依存する場合はC待ちを維持する。
- 全体変換の依存順序、循環処理、空き枠補充、同時実行上限を維持する。

## 4. R3：runtimeの工程06の承認状態を表示する（P2）

### 再現と原因

runtimeでparityまで成功し、現在の結果に対する `approve post-parity` が有効でも、
statusはその承認を読まず、工程06をpendingとして再承認を案内する。

### 実装方針

1. runtimeで現在のparityが有効な場合、`requireGate('post-parity')` 相当の既存検査で
   post-parity承認を確認する。ファイルの存在だけでは承認済みにしない。
2. 有効な承認があれば、工程06は `approved` 等の「承認済み・作業完了未確認」と表示し、
   次の行動を「承認済みのprompt 06の整理作業を実施し、結果を報告する」とする。
   再承認は案内しない。工程名もruntimeではPost-parity cleanupとする。
3. 未承認なら、現在のparity結果をレビューして承認する既存案内を維持する。
   壊れた・古い承認は理由を示し、上流の再実行や出力変更による失効を反映する。
4. 承認を工程完了と取り違えない。runtimeに新しい完了receiptや
   `run_migration.mjs post-parity` コマンドは追加しない。
5. source-onlyの工程06は既存のhandoff記録で判定する。
   runtimeの承認と混同せず、equivalenceはunverifiedのままとする。

### 受け入れ条件

- 有効なpost-parity承認後は再承認を案内せず、JSON/Markdownの工程06が承認済みと分かる。
- 承認ファイルなし、不正JSON、入力変更、parity再実行後に承認済みと誤表示しない。
- source-onlyのhandoff完了表示を維持し、statusはファイルを書き換えない。

## 5. R4：予約数と実際のアダプター呼び出し数を分ける（P3）

### 再現と原因

concurrency=1で最初のreviewerが失敗すると、予約済みのもう一方は呼ばれない。
しかし予約時の `calls++` により、実装1回＋レビュー1回なのにsummaryは3回と報告する。

### 実装方針

1. 上限管理に使う予約数と、表示・summaryに使う実際の呼び出し数を内部で分ける。
2. 予約数は非同期の空き枠待ちより前に確保し、maxAgentCallsを超える予約を防ぐ。
   上限到達時も、それ以前に予約された呼び出しを取り消さない既存動作を維持する。
3. 実際の件数は、キャンセル・停止・入力の再検査を通過し、adapterを呼ぶ直前に加算する。
   呼び出したadapterが失敗した場合は1回、呼ぶ前に止まった場合は0回とする。
4. summaryの `agentCalls` と進捗通知の `calls` は実際の件数を使う。
   保留・中止の試行記録は調査用に残してよいが、AI呼び出し済みと偽らない。
   これはワーカーアダプターの呼び出し件数であり、providerの課金・トークン計測ではない。
5. 公開する設定やモデル指定、料金推計の新機能は増やさない。

### 受け入れ条件

- 実装1回＋失敗レビュー1回で、実際の呼び出しもsummaryも2回になる。
- 空き枠待ち中にキャンセル・入力障害で止まった呼び出しを加算しない。
- 呼び出し上限2の既存CLI/nativeテストで、実装と最初のレビューは実行され、
  次回は不足したレビューだけを呼ぶ。上限・同時実行数を超えない。
- 通常デモは従来どおり3単位・9呼び出しで完了する。

## 6. 実装と検証の順序

1. 再現ケースを既存のテスト補助関数で回帰テストにする。保留Promiseや明示的な
   同期点を使い、単なる短いsleepへの依存と未終了プロセスを避ける。
2. pipelineの実行寿命と呼び出し件数、全体依存グラフの扱いを修正する。
3. statusのpost-parity承認分岐を修正し、必要な運用説明をそろえる。
4. 関連テストを実行し、その後 `npm test`、`npm run demo`、`git diff --check` を実行する。
5. 親は差分を読み、前回の独立再現用スクリプトも使って4件の解消を確認する。
   重大な問題が残れば実装担当へ戻し、修正後に必要な検証を再実行する。

親の再現用スクリプトは現在の作業環境の `/tmp/migration-second-review.mjs`。
変更前との比較用は `/tmp/migration-baseline-review.mjs`。
R1は修正後に「途中のロック保持」も検証できる形へ親が調整する。
実機でのTODO描画・Rubber Duck・モデル委譲の検証状況は、今回の自動テストで更新しない。
