ここで一度だけ決めます。決めないと、エージェントごとに違う書き方になり、

## 2. 対応するものがない構文 — それぞれ正規の対応を1つだけ

移行先にない元の構文には、翻訳を必ず1つだけ決めて、ここに書きます。
載っている構文に2つ目の対応を作った変換役はルール違反です。
載っていない構文を見つけたレビュアーは、この表に加えるよう指摘します。

| 元の構文 | 移行先での正規の翻訳 | 備考・根拠 |
|---|---|---|
| [例: エラーユニオン／例外] | [例: この E を使った Result<T, E>] | |
| [例: null／省略可能な値] | [例: Option<T>。番兵値は使わない] | |
| [例: 継承] | [例: トレイト＋合成。この形にする] | |
| [例: 範囲外の添字] | [元は例外を投げる／番兵値を返す／未定義動作 — 元の動きを明示的に再現する。元が例外を投げるところで黙って undefined を返す移行先は、不具合を量産する] | |
| 識別子の先頭での `isalpha()` — **記入例、C 系の元コード** | [識別子の先頭と2文字目以降に使える文字の集合を明示的に決める。移行先の「英字か」判定の関数を確認せずに使わない] | 移行先の判定関数は、下線とロケールの扱いが C の `isalpha()` と違う — Run 2 では先頭の `_` を受け付けたため、エラー位置が1バイトずれた |
| [調査で見つかったら行を足す] | | |

**BUG ルール:** 元の動き自体が不具合（出力が壊れる、落ちる）のときは、
不具合ごとそのまま再現し、再現手順を添えてその箇所に `BUG(port):` を付けます。
動作の一致確認（Step 6）は不具合のある出力を正とします。直すのは、一致確認の後に
印を付けた別の変更でだけ行います。移行の役目は忠実さで、改善はレビューできる別のコミットです。

**エラー回復ルール:** 元のコードでは、メモリ確保の失敗と構造エラーが同じ番兵値
（NULL、None、-1）を返すことがよくあります。移行先では同じ構文にしてはいけません。
メモリ確保の失敗は処理を中止します。構造エラーはエラーを記録し、元が返していた
途中までの結果を返します。inventory のガードの行には、どちらの種類かを必ず記録します
（`allocation-guard` または `precondition-guard`。`templates/inventory.tsv` を参照）。
Run 2 では2つを同じに扱ってエラー位置を間違え、その後のルール見直しで、
テストがなかった箇所をさらに3つ直しました。

**UNKNOWN ルール:** この表でも inventory でも決まらない場合は、移行先で
いちばん控えめな表現に翻訳し、未解決の問いを書いた `TODO(port):` を付けて先へ進みます。
UNKNOWN も1つの答えです。止まったバッチは答えではありません。

## 3. 認められた逃げ道

安全に表せない翻訳には、逃げ道を1つだけ用意し、見える形で使います。

- [例: `unsafe` は元が既に unsafe だった箇所でだけ使う。安全な処理で
  借用チェッカーを黙らせるためには使わない。]
- 使うたびに理由のコメントを付けます: `// SAFETY: <なぜ正しいか>`。
- 先送りした判断には、検索できるマーカーを必ず付けます: `TODO(port):`、
  `PERF(port):`、`BUG(port):`（逃げ道を使った箇所には `SAFETY:` も）。
  これらのマーカーは後の工程の作業一覧になります。書式に意味があるので、変えないでください。

## 4. 名前と出力先

完了には、入力の文脈と出力のハッシュを結び付けた、最新のレビュー済み記録が必要です。
ファイルがあるだけでは完了ではありません。出力先の対応は重複させず、
config の outputRoots の中に収めます。

- 元 `[パスのパターン]` → 移行先 `[パスのパターン]`。元の1ファイルを移行先の1ファイルにします。
  例外はここにルールがあるときだけです。
- [モジュール・パッケージの名前の付け方。]
- [テストファイルの名前の付け方。]
- 移行先のモジュール方式での import の書き方（例: TS の nodenext では、
  `.ts` ファイルにも `./mod.js` と書く必要がある。一度決めないと、変換役が毎回調べ直す）。
- 翻訳したコードが import する共有の型と補助関数ごとの置き場所（値のユニオン、
  型による分岐の補助、repr の再現などを持つ正規のモジュール）。置き場所を決めない共有の型は、
  互換性のないローカルのコピーが何個もできる原因になります。

## 5. ギャップの一覧（inventory）

[あなたのギャップ — 寿命、所有権、null になり得るか] に関する判断は、
**変換役がしません**。`migration/inventory.tsv`（1箇所につき1行）で調べます。
自分の箇所が inventory にないときは inventory の不具合です。指摘し、UNKNOWN ルールを使い、
先へ進みます。

## 6. ファイルごとの義務

翻訳したファイルは、最後に状態の行を付けて終えます。

```
// PORT STATUS: confidence=medium todos=2
```

これは書き方の例です。`confidence=` には `high`・`medium`・`low` のどれかを、
`todos=` には `TODO(port)` を含む行の数を数字だけで書きます（角括弧は付けません）。
コメントは移行先の1行コメントの書き方にし、ファイルの最後の閉じ括弧の後に置きます。
クラスや関数の中には置きません。
レビュアーは、この行をファイルの実際の `TODO(port)` の数と照らし合わせます。
多く数えている行も、少なく数えている行も指摘の対象です。

config の markerPolicy が `todo-lines-v1` のときは、マーカーを含む行の数を数えます
（1行に2つあっても1と数えます）。PORT STATUS の行は、空でない最後の行に1つだけ置き、
数はこの数え方と一致させます。両方のレビュアーに測った結果が渡され、
コーディネーターも食い違いがあれば完了前に差し戻します。この方針を使わない既存の
プロジェクトは、明示的に合意した従来の決まりを続けます。キットの docs/EXECUTION-SCOPES.md を参照。

## 7. 逸脱の記録

決められた手順から外れたことは、すべてここに1行ずつ書きます。飛ばした工程、
免除した確認、発動しなかった既定値などです。`DEV-001` の形の ID を付け、ID、日付、
飛ばした・免除した内容、誰が認めたかを書きます。関門で、人間が書くか、
人間の了承を得て書きます。誰も記録していない逸脱は、誰も認めていない逸脱です。
