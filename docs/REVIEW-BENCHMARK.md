# ワーカーを統合する前に測る（レビュアー数・fixer）

日本語 | [English](REVIEW-BENCHMARK.en.md)

翻訳ループの担当構成を簡素化すると、呼び出し回数や時間を減らせる可能性があります。ただし効果と品質への影響は、測らないと分かりません。このベンチマークは、次の2つの案を、欠陥を埋め込んだ同じ題材と同じ Copilot CLI ワーカーで比べます。

| 比較 | 現行 | 統合案 | 見る数字 |
|---|---|---|---|
| レビュー | 独立した2レビュー＋裁定 | 1レビュー（両観点）＋裁定 | 裁定後の見逃し率、欠陥なし題材での誤検出 |
| 修正 | fixer | implementer に確定指摘を渡す | 修正後の動作チェック合格率 |

翻訳ループの動作は変えません。結果を見て、統合するかどうかは人が決めます。

修正側は、毎回新しい CLI セッションで fixer の仕事を implementer に任せられるかを測ります。どちらも修正の呼び出しは1回です。実装時の文脈を引き継ぐ効果や、修正呼び出し自体の削減は測りません。

## 背景

Anthropic の記事「[Building agents: When to fold subagents into your main agent loop](https://claude.com/ja/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)」（2026-10-22）は、サブエージェントを畳むときの進め方として次を勧めています。

- 先に小さな評価を作り、畳むのは一度に1つだけにする。スコアが下がったら分けたままにする。
- スコアだけでなく、どのタスクの結果が変わったかを見る。
- 壊れ方は毎回出るとは限らない（記事の例では2回に1回）。各タスクを複数回実行する。

記事の判断基準では、「出力を順に受け渡す」「同じデータを触る」役は統合の候補です。fixer は implementer と同じツール・同じ出力形式で、この条件に当てはまります。レビュー1人の案でも、生成担当から独立した検証は残ります。2人目のレビューが品質にどれだけ寄与するかを、ここで測ります。

## 手順

モデル呼び出しには利用枠・料金が発生します。題材は `fixtures/mini` の3ファイルです。

1. キットのルートで、まだ存在しないディレクトリを指定して検証用のルートを作ります。

   ```bash
   node scripts/review_benchmark.mjs setup --target /tmp/review-bench --model MODEL_ID
   ```

   ワーカーはルートのファイルを読めます。そのため setup は、ルートからこのベンチマークの文書・コード、比較器の mutant などを除きます（過去のレビュー・検証記録は `history/` にあり、導入先には写りません）。正しいコードの行が残っていれば setup は失敗します。ただし CHANGELOG などには、ベンチマークがあること自体は書かれています。全担当に同じモデルが入ります。担当ごとに変える場合は `/tmp/review-bench/migration/config.json` の `models` と `reasoningEfforts` を編集します。レビューの観点は `reviewFocus: "shared"` に設定されます（1人のレビューでも両方の観点を見るため）。

2. まず1回ずつ、検証用ルートとワーカーが動くことを確認します。呼び出し回数の上限を表示します。

   ```bash
   node scripts/review_benchmark.mjs plan --root /tmp/review-bench
   ```

   既定は各題材1回で、9題材では最大59回です。内訳は、レビュー2人が27回、レビュー1人が18回、修正が14回です。裁定は指摘があったときだけ呼ぶので、実際の回数は上限以下になります。`--part review|fix` で片方だけ、`--cases math-trunc,text-trailer` で題材を絞れます。同時AI呼び出し数は、2人のレビューも含めて設定の `concurrency` 以下です。

3. plan で表示された `total` を `--max-calls` に指定して実行します。

   ```bash
   node scripts/review_benchmark.mjs run --root /tmp/review-bench --max-calls 59
   ```

   結果は一時ディレクトリの `review-bench-results/<時刻>/` に出ます（場所は実行後に表示されます）。ワーカーはルートを読めるので、結果をルートの中に置くことはできません。`--out` で場所を変えられます。一時ディレクトリもワーカーが読める場合があるので、結果は実行の最後にまとめて書きます。修正結果のファイルも、チェックを動かす間だけ乱数名で置きます。setup で作っていないルートや、題材の出力先にファイルがあるルートでは、何も書かずに止まります。

   | ファイル | 内容 |
   |---|---|
   | `report.md` | 比較表と、結果が変わった題材の一覧 |
   | `summary.json` | 集計 |
   | `results.jsonl` | 1回ごとの全指摘・照合結果・トークン |
   | `fixes/` | 修正結果のファイル |

   1回も成功しないまま3回失敗したとき（ログインやモデルIDの誤りなど）は、何も測らずに止まります。実行中の呼び出しを止め、新しい呼び出しも始めません。並列実行では、先に始まっていた呼び出しの失敗も数えます。不正な応答が1回あっただけなら、その回を失敗として記録して続けます。Ctrl-C で止めたときは中断として扱います。

4. 統合するか判断するときは、同じ条件を複数回測ります。1回だけでは、たまに起きる見逃しを判断できません。たとえば3回なら最大177回です。再び plan を確認し、別の結果ディレクトリへ記録します。

   ```bash
   node scripts/review_benchmark.mjs plan --root /tmp/review-bench --runs 3
   node scripts/review_benchmark.mjs run --root /tmp/review-bench --runs 3 --max-calls 177
   ```

   小さな題材から評価を始め、実案件に近い題材を足して判断します。1回の確認結果だけでレビュー担当を減らす設定にはしません。

## 題材と照合

| 題材 | 欠陥 | 種類 |
|---|---|---|
| math-trunc | 商を `Math.trunc` で切り捨て（Python は floor） | 意味 |
| math-remainder | 剰余に JS の `%` を使用（符号が違う） | 意味 |
| math-zero | ゼロ除算の例外がない | 意味 |
| math-double | trunc とゼロ除算の2件 | 意味 |
| text-length | `name.length`（UTF-16 単位で数える） | 意味 |
| text-trailer | PORT STATUS の末尾行がない | 規則 |
| main-import | `./math_ops.js` を import（規則は .mjs） | 規則 |
| control-math / control-text | 欠陥なし（指摘はすべて誤検出） | — |

- 指摘が欠陥の行をそのまま `パス:行` で挙げているか、欠陥ごとの語句（`pattern`）に当てはまれば、見つけたと数えます。1つの指摘で数える欠陥は1つまでです。行の一致を語句より優先し、語句だけで複数の欠陥に当たる指摘はどれにも数えません（`ambiguous` と記録します）。trunc とゼロ除算の両方を述べた1つの指摘も、片方にしか数えません。語句は狭めにしてあり、行を挙げずに「b が 0 のときの確認がない」とだけ書いた指摘などは数えないことがあります。そのため見逃し率は多めに出ることがあります。条件は両方の案で同じです。機械的な照合なので、判断の前に `results.jsonl` の指摘を目で確かめてください。
- 修正の比較では、両方に同じ正解の指摘を渡します。レビューのばらつきを修正の比較に混ぜないためです。修正後のファイルは `fixtures/review-bench/checks/` の動作チェックで判定します。`main` は採点専用の一時ディレクトリで正しい依存モジュールと組み合わせ、標準入力から実行して出力を比べます。引用符の種類で合否は変えません。未変更で返したとき、出力が違うとき、生成コードが時間内に完了しないときは不合格です。モデル呼び出しや検査プロセスの起動自体が失敗した回は、別の失敗欄に記録します。
- 裁定は、全指摘への回答が一度ずつそろっていることを本番ループと同じ条件で確認します。回答漏れ・未知の指摘・重複した回答は、その回の失敗です。
- 全題材で、最後の非空行に PORT STATUS コメントが必要です。先頭コメントや文字列に語句があるだけでは不合格です。末尾の空行や CRLF は許容します。
- トークンは失敗した回も含めて合計し、どれかの呼び出しで取得できなければ `unknown` にします。トークン数は実料金の計測ではありません。
- チェックはモデルが返したコードを Node で実行します。環境変数は PATH と一時ディレクトリだけを渡し、資格情報は渡しません。それでも隔離はされないので、使い捨ての環境で実行してください。
- 題材を足すときは `fixtures/review-bench/cases.json` に書きます。欠陥ありの題材はチェックに落ち、欠陥なしの題材は通ることを `tests/review-benchmark.test.mjs` が確かめます。

## 判断の目安

記事の原則（スコアが下がったら分けたまま）に沿って、次をすべて満たすときだけ統合を検討します。

- **レビュー**：レビュー1人の裁定後の見逃し率がレビュー2人以下で、「Cases that changed」にレビュー1人が少なく見つけた欠陥がない。欠陥なし題材での確定した誤検出も増えていない。失敗した回があって回数がそろわない題材は、注記が付きます。回数をそろえて測り直してください。
- **修正**：implementer の合格率が fixer 以上で、合格回数が減った題材がない。

差がなくても、統合して安全だという証明にはなりません。題材は小さな3ファイルで、欠陥は8件だけです。実案件に近い難しい題材を足してから判断することを勧めます。統合すると決めた場合も、翻訳ループの変更は別の変更として入れ、同じベンチマークで確かめ直します。
