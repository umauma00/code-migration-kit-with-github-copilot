## 実装した内容

- 工程TODOと質問の担当を、利用者と会話する親に統一。実際に公開されたTODOツールの
  応答を確認し、利用不可・失敗・非表示の場合は同じ一覧をチャットに出す。
- `status --format markdown` を追加。準備不足、実装開始条件、現在の工程・役割、
  レビュー済み件数、停止理由、次の行動を表示する。残り時間は未算出と明記する。
- 00・00bの問題報告に、根拠、修正内容、担当、完了条件、実装開始を妨げるかを含める。
- `verificationMode: "source-only"` とjudge準備記録、smoke後のhandoff経路を追加。
  元環境を動かさずに進め、最終結果は「ソース基準の移植完了・動作同等性未検証」とする。
  runtime方式のoriginal/mutation/parity、両方式の独立2レビュー・承認・失効条件を維持する。
- 並列処理を、空いた枠に依存条件を満たす単位を追加する方式に変更。
  全AI呼び出しに既存の同時実行上限を適用し、依存順序・循環・停止・再開を扱う。
- 実際の組み込みRubber Duckを節目で呼び、指摘の採否・修正・再検証を記録する手順と
  テンプレートを追加。native runnerの実行中は仕事の受け渡しを継続する。

言語別テンプレート、モデル配分・費用管理、新しい中断再開機能は合意どおり対象外。

## 差し戻した主な指摘と確認

| 指摘 | 修正と確認 |
|---|---|
| 呼び出し上限に達すると、予約済みの最後のレビューまで止まり、原因も一般的な停止メッセージに隠れる | 予算による新規予約の停止と、実際の障害による呼び出し停止を区別。既存の2件の上限・再開テストを維持して成功。障害後に待機中のレビューや次の単位を開始しないことも検証 |
| 実行中のビルドを未着手・不完全な記録と表示し、再実行を勧める | ロックの実行IDと工程記録を照合して実行中と表示。保留したビルドで監視案内を確認し、古いIDでは実行中と判定しない |
| 実行中の変換にも再実行を勧める | translation/repairの実行中は監視を案内。native方式では親が仕事の受け渡しを継続するよう表示 |
| 空のmanifestでも実装開始可能と表示する | 有効な単位が1件以上あることを開始条件に追加。judgeと承認が存在しても空なら開始不可 |
| 状況収集がnativeの任意の回答JSONまで読み込む | 調整役の試行記録だけを読む。無関係な回答や不正な1件が他の稼働記録を隠さないことを検証 |
| source-only説明と、元環境・parityを必須にする既存の指示が矛盾する | 共通指示、00/00b/06、運用手順、工程表、READMEで方式を明示して分岐 |
| Rubber Duckのためにnative処理を止めて待つと、親が仕事を受け渡せなくなる | runnerと子の実行が終わった工程の境目で実施する手順へ整理 |
| source-onlyのコマンドなし工程が、既にキャンセル済みでも成功する | 開始前にキャンセルを確認。既存の記録と承認を変更せず拒否することを検証 |
