# Dependency mappers (bundled and project-written)

[日本語](DEPENDENCY-MAPPERS.md) | English

Phase 01's dependency map comes from a **deterministic mapper that only reads source text**. It never builds or runs the original application. [Source as the only specification](SOURCE-AS-SPEC.en.md) uses the same mappers.

## Bundled mappers

All of them need only the Python 3 standard library (nothing to install; Windows, macOS and Linux alike).

| Source language | Command | Where edges come from |
|---|---|---|
| Python | `python3 migration-kit/scripts/depmap_python.py --root src --out migration/depmap` | imports (parsed with ast) |
| JS / TS | `node migration-kit/scripts/depmap_ts.mjs --root src --out migration/depmap` | import / export from / require |
| C / C++ | `python3 migration-kit/scripts/depmap_c.py --root src --out migration/depmap` | `#include "..."`, same-stem header |
| C# | `python3 migration-kit/scripts/depmap_csharp.py --root src --out migration/depmap` | type names (namespaces, using, global using, aliases, using static, extension methods, partial types) |
| Java | `python3 migration-kit/scripts/depmap_java.py --root src --out migration/depmap` | type names (same package, imports, `pkg.*`, static imports, qualified names) |
| VB.NET | `python3 migration-kit/scripts/depmap_vbnet.py --root src --out migration/depmap` | type names and Module members (Imports, RootNamespace, case-insensitive) |
| PHP | `python3 migration-kit/scripts/depmap_php.py --root src --out migration/depmap` | include / require paths; class, function and constant names (namespace, use) |
| COBOL | `python3 migration-kit/scripts/depmap_cobol.py --root src --out migration/depmap` | COPY, EXEC SQL INCLUDE, CALL 'PROG', EXEC CICS PROGRAM(...) (LINK, XCTL, START, LOAD, HANDLE ABEND, RELEASE, ENABLE) |

On Windows use `py` or `python` instead of `python3`.

Extra options (comma-separated paths relative to `--root`):

- PHP: `--include-var phpbb_root_path=phpBB/,phpEx=php` gives the values of variables (`$NAME`) and constants (`NAME`) used in include paths (a directory is relative to `--root`). A variable inside a `"..."` string or heredoc (`"$IP/includes/x.php"`) is replaced too (`$IP` inside `'...'` is text). A constant every `define()` gives the same relative literal (`define('WPINC', 'wp-includes')`), and one defined as a path the mapper can compute (`define('DO_MAINTENANCE', dirname(__FILE__) . '/doMaintenance.php')`), is used without it, unless another `define()` of it gives a different value. Drupal's `.install`, `.test`, `.theme`, `.engine` and `.profile` files are read as PHP when they contain `<?php`. `--include-path lib,inc` gives PHP's include_path. A relative include is looked up there first, then next to the including file, then at `--root`. An explicit `./x` or `../x` is relative to the working directory and never uses include_path: it is looked up next to the including file and at `--root`; when those give two different files, both become edges and the include is listed in `unresolved.tsv`. `composer.json` autoload (PSR-4, PSR-0, classmap; not under vendor) is read automatically: a class declared in several files maps to the one autoload names.
- COBOL: `--copy-path copy,shared` gives the copybook search order (like SYSLIB or COBCPY). When a copybook name matches several files, the first listed directory wins; `COPY X OF LIB` looks first in a directory named LIB. A `*>` inside a literal (`DISPLAY '*>'`) is not a comment, and a tab in fixed format advances to the next multiple of 8 columns. An EXEC CICS `PROGRAM(...)` is read only up to its END-EXEC.

Every mapper writes:

- `edges.tsv`: one edge per line (from → to, paths relative to `--root`)
- `order.txt`: migration order, dependencies first, a cycle on one line
- `cycles.txt`: cycles of two or more files
- `unresolved.tsv` (C#, Java, VB.NET, PHP, COBOL): references the mapper saw but could not tie to a file, with the reason: computed includes, CALL through a data item, reflection with a computed name, an import of a type the repository's package does not declare

The same input always gives byte-identical output. Shift_JIS (cp932) sources are read too: a file that is not UTF-8 is read as cp932, then Latin-1, with a warning. A file that decodes as cp932 without a single kana or full-width punctuation mark (Western Windows-1252 text) is read as Latin-1. UTF-16 and UTF-32 are recognised by their byte order mark. UTF-16 without one is read only when every other byte is NUL, with a warning; any other file holding NUL bytes is not text, is not analysed, and is listed in `unresolved.tsv` as `(whole file)`.

## Accuracy (typed languages)

In C#, Java and VB.NET an import names a namespace, not a file, and types of the same namespace need no import. The mappers build a table of the types each file declares and resolve every name **written** in each file's code against it.

- **They follow types whose name is never written.** A table of each type's declared method, property and field types and its base types lets the mappers follow variables and call chains: in `var x = F(); x.M().N();` the return types of `F`, `M` and `N` become edges. Parameters, typed locals and foreach variables count; an element type such as `List<Order>` passes through indexers and LINQ-style calls.
- **Names resolve in the language's order.** Each name is looked up from the namespace block it is written in (a file with several blocks resolves each on its own). A using, alias or using static inside a block applies to that block and the blocks nested in it, not to another block of the same namespace. C# and VB.NET go from the innermost namespace outward one step at a time, and at each step look at that namespace's types, then at the aliases and usings written in its declaration (file-level and global usings form the last step; a using after `namespace N;` belongs to N); `global::X` / `Global.X` start at the root namespace; Java takes single-type imports, then its own package, then `pkg.*`. Candidates tied at the same level all become edges (leaning towards extra edges); a local variable named like a type becomes one too. `using static T` brings T's members and nested types, not the name T; `[Foo]` written as an attribute (`[Foo<int>]` and attributes on lambdas and finalizers too) counts both `Foo` and `FooAttribute` (C# takes the one that is an attribute), and `Foo` elsewhere (collection expressions such as `F([Foo])` or `{ [Foo] }` included) does not mean `FooAttribute`. A tuple or other non-name alias (`using P = (A a, B b);`) gives edges to its types from the file that writes it (for a global alias, that file only).
- **Project files narrow candidates.** C# and VB.NET read ProjectReference in `.csproj`/`.vbproj`; Java reads Maven (`pom.xml`) and Gradle (`build.gradle`) module dependencies. When a type name exists in several projects, only the referenced projects' files become edges. A file the build leaves out (`<Compile Remove>`, or missing from an old-style project's `<Compile Include>` list) declares nothing and is listed in `unresolved.tsv`. Include/Remove values are item lists (`a.cs;b.cs`). Wildcards follow MSBuild: `*` and `?` stay within one directory, `**` spans any depth. Attribute values may use either quote. An Include's `Exclude` applies to that Include only (`Include="**\*.cs" Exclude="Legacy\**"`); `Update` only changes metadata and is not read. Include and Remove apply in document order (`Include="Legacy\Keep.cs"` after `Remove="Legacy\**"` compiles Keep.cs again). Conditions and properties (`$(Gen)`) are not evaluated: a file added or left out only under a Condition (on the item, its ItemGroup, a `<Choose>` branch, or inside a `<Target>`) or by an item that uses a property keeps its declarations and is listed in `unresolved.tsv`. A file of another directory pulled in with `<Compile Include="..\Shared\X.cs" />` is also a file of the project that pulls it in (that project's global usings, references and VB RootNamespace apply; an alias that means a different type in each project gives an edge to each; and it is compiled even if its own project leaves it out). An SDK project that turns the default items off and lists no `<Compile>` makes its files "maybe" (an import the mapper does not read may list them). Default files need both `EnableDefaultItems` and `EnableDefaultCompileItems` on; either one set to false under a Condition makes the default files "maybe". A ProjectReference must match the project file's whole path (case is ignored); one that names a file that is not there is warned about. Maven dependencies match by groupId:artifactId: modules with the same artifactId under different groupIds are different modules. A groupId the mapper cannot read (a property) keeps every module of that artifactId as a candidate, with a warning. Gradle `project(":core")`, `project(path: ":core")`, Kotlin's `project(path = ":core")` and type-safe accessors (`projects.core`; `my-lib` is `projects.myLib`) are read. global using directives and aliases, `<Using Include>` and `<Import Include>` apply to the files of their own project. An alias with several targets (`<Using Alias>` items split by Debug and Release Conditions) gives an edge to each, with a warning. `<Using Include="A;B">` is an item list, and `Alias` and `Static` are read as child elements too (`<Using Include="Lib.A"><Alias>X</Alias></Using>`); a Condition on such an element is not evaluated: it is applied as if it held, with a warning, and several `<Alias>` elements of one `<Using>` (one per Condition) all apply. A `<Using>` holding a property (`$(NS).A`) cannot be evaluated, so it is not applied; it is warned about and listed in `unresolved.tsv` under the project file (VB `<Import Include>` too). VB `Imports Global.X` names X from the root, and an Imports continued over lines is read. A global using in a file the build leaves out applies to no file. XML comments (`<!-- ... -->`) in project files are not read. A shared file outside every project directory that a project pulls in only under a Condition is listed in `unresolved.tsv` too. `global using static` (and `<Using Static="true">`) gives an edge from each file of the project that names a member of the type. A tag with a raw `<` in an attribute value (invalid XML that MSBuild cannot load either) is not read and is warned about with its line number. The files are read as text; MSBuild and Maven are never run.
- **Extension methods are narrowed by receiver type.** `x.Name()` gives an edge to an extension method `Name` of a visible namespace. A static call (`string.Join(...)`, `Math.Min(...)`) does not count. When `x`'s type is known (a variable, parameter, field or `this`), only extension methods whose receiver type matches become edges, and none when that type has a member of the name. When it is not known, the name is also a member of common framework types (`Add`, `Contains`, `Select`...) and the extension's receiver is a framework type too, the call is listed in `unresolved.tsv` instead of becoming an edge.
- **Nested types** (a class or delegate inside a class) are not duplicates of a same-named type. Inside the file that declares it, a nested type's name means that type (many Java classes each nesting a `DescriptorImpl` get no edges to each other's), and `Outer.Inner` means it anywhere. Other files cannot see it by its simple name, so a nested type of an outer namespace does not hide a using's type of the same name (it becomes an edge only when nothing else has the name); elsewhere, where a top-level type of that name exists, the name means it. VB.NET works the same way, except that a type inside a Module counts as a type of the namespace, not a nested one.
- A name a declaration introduces (C# `Schema`, `bar`, `Run` in `public string Schema {`, `Foo bar =`, `void Run(`; Java `int Customer;`, `void Order()`; VB `Property Customer As Integer`, `Sub Order()`, and parameters and locals such as `customer As String` or `Dim order`) and an enum member (`enum EntityType { Customer, Order }`, also a sibling written in a value, `Both = Order | Customer`, or in a Java constant's arguments, `Bar(Gadget)`; a Java annotation on a constant, `@Ann A` or `@a.b.Ann(x) A`, is a reference to the annotation type) are not type references (a member named like a type gave a false edge and a false cycle).
- **A type declared without partial in two files**: the two are not linked to each other (that would be a false cycle). Files that use the type get an edge to both, and `unresolved.tsv` lists it as "also declared in ...". One copy is probably left out of the build or belongs to another project; check it. Members of VB modules (`Sub Log` in two modules) are not duplicates.
- **Still missed:** lambda parameter types, a top-level type used from another class of a file that nests a type of the same name (inside that file the name means the nested type), generic method type inference, overload resolution, `dynamic`, VB With blocks. Check that review evidence is complete with the [preparation audit](PREPARATION-AUDITS.md) samples and `dependency-diff`.
- A PHP function, class or constant the file declares itself means that declaration. Of several declarations, the ones the file's includes reach (transitively) win; when none is reached, all become edges (core files linked to `define()` copies in develop/ scripts).
- A PHP declaration behind an existence check (`if (!function_exists('f')) { function f() ... }`, a back-compat fallback) is linked only where no unguarded `f` exists (core linked to every theme's fallback copy, a false cycle); when only guarded copies exist, they are the declarations.
- PHP decides `$obj->m()` at run time, so a full parser cannot resolve it either, and COBOL dependencies are just COPY and CALL names: for these two a real parser adds little. The bundled mappers still read only written names and paths they can compute (`__DIR__`, `dirname(__FILE__)`, `DIRECTORY_SEPARATOR`, `DS`, `realpath()`); the rest goes to `unresolved.tsv`. Code inside `{$...}` holes of `"..."` strings and heredocs counts (nowdocs are text; a quoted literal such as `'Order'` inside a hole and `${name}` are not names). A `class_alias(Orig::class, 'Old')` (or `\class_alias('Orig', 'Old')`) alias is a class of the file that calls it; a computed alias name is listed in `unresolved.tsv`. A PHP string callable gives an edge to the function or class of that name only as a string argument in a callback position of a function that takes a callback (`array_map`, `usort`, `call_user_func`, `add_action`...) or in a `['Cls', 'm']` pair. Data arguments (`business` in `call_user_func('strtolower', 'business')`, the hook name in `add_action('init', ...)`), array keys and other plain strings are not references. Named arguments are read by each function's parameter names (`call_user_func(callback: 'f')`, `preg_replace_callback_array(pattern: [...])`, `session_set_save_handler(open: ..., update_timestamp: ...)`; all nine session handlers are read, and the handler-object form gives an edge for `new Cls` and an `unresolved.tsv` row for a variable). `['Cls', 'm']` gives an edge to `Cls` with a trailing comma, as `array(...)`, and with a variable method name (`['Cls', $method]`) too, and the strings of `is_a($x, 'Cls')` and `is_subclass_of` are class names. A callback argument that is not a string without variables, `null`, a closure, `f(...)` or a pair whose class is fixed (`[$this, 'm']`, `['Cls', 'm']`, `['Cls', $method]`, `[Cls::class, 'm']`, `[new Cls, 'm']`) (`call_user_func($cb)`, `usort($a, $this->cmp)`, `"on_$x"`, `'on_' . $x`, `get_callback()`, `[$class, 'm']`...) and a variable function call (`$f()`) are listed in `unresolved.tsv`. The tables of functions that take a callback or a class name are closed: besides the ones above, `mb_ereg_replace_callback`, the `xml_set_*_handler` functions, `stream_wrapper_register` and `new ReflectionClass`/`ReflectionMethod` are read; a string passed to any other function is not. A variable where a class name is taken (`new ReflectionClass($name)`, `is_a($x, $cls)`) is often an object, so it is not listed in `unresolved.tsv`. An include inside an expression (`if (!include_once 'x.php') {`) takes its path up to its own parenthesis or operator. `namespace\f()` names the current namespace's f only (never a `use function` import or the global function) and is not a namespace declaration; one not under `--root` goes to `external.tsv`, as `\App\Billing\Invoice` would; an `f()` imported with `use function A\f;` names that function only. An include inside an expression also ends at `or`, so the right side of `include 'a.php' or fallback();` is read as code. An include whose place `__DIR__` or `dirname(__FILE__)` fixes, and whose file is not there, is listed in `unresolved.tsv` instead of linking a same-named file elsewhere.

## Checking a mapper's output

1. Five-file trial: run on five files before the whole tree and show `edges.tsv` and `unresolved.tsv` to the user.
2. Read every row of `unresolved.tsv`: external libraries are fine; anything that should point at a repository file goes into `review-dependencies.json`.
3. Look for in-house libraries in `external.tsv`: the C#, VB.NET, Java and PHP mappers write each namespace or package no file declares (a using, Imports or import; a full name written where a type stands: `Acme.Billing.Invoice inv;`, `new`, every type of a base list or `where` constraint, every type after Java extends/implements/throws, an attribute or annotation; a PHP namespaced name), one row per namespace (namespace, number of files using it, first file). A namespace whose parent is also listed folds into the parent's row (`log4net.Config` into `log4net`); siblings (`com.fasterxml.jackson.databind` and `com.fasterxml.jackson.core`) get a row each. Platform namespaces are left out: System, Microsoft, Windows, Mono, and java, javax, jakarta, jdk, sun, com.sun, org.w3c, org.xml and the like (javax and jakarta as a whole, so `javax.inject` and `jakarta.persistence` are left out too). A C# or VB.NET full name written in code counts only when its namespace part has two segments or more (or `global::`), since `Environment.SpecialFolder` may be a platform class's nested type. In a file with `Imports System` or `using System`, a name starting with a namespace under System (Collections, IO, Net, Text, Data and the like: `Collections.Generic.List`) is taken as relative to System and not counted. Full names in generic arguments (`List<Acme.X>`), nullable types, tuple elements, casts and Java `Acme.X.class` are not read (they are listed when the same namespace is also imported). Java rows are always packages, the lower-case segments before the first type (`import static a.b.Util.*` gives `a.b`). PHP rows come from the names code writes (`use Acme\Billing;` with `Billing\Invoice` gives `Acme\Billing`; a `use` no code uses is taken as a class); PHP namespaces are matched case-insensitively, and PHP's own `Random`, `Dom`, `Pdo`, `BcMath`, `Uri`, `FFI` and the like are left out. VB.NET names are written with the casing they were first written in; common third-party libraries such as Spring or log4net are listed and are fine. An in-house library whose source is outside `--root` gets no edges, so when one shows up here, map again with a `--root` that also holds its source. With no source (only a DLL or JAR), decide with the user how the migration treats that library (port it too, or keep using it).
4. Check that the skipped directories (listed at the top of each script) suit the project. Build output (bin, obj, target, build, out), vendor and packages are skipped only at `--root` or beside a build file (.csproj, pom.xml, composer.json...); a package or folder with the same name is read. A skipped directory holding sources is printed as a warning (`WARN skipped ...`). Directory symlinks are followed (a directory seen under two paths is read under both); only a loop back to an ancestor is stopped, with `WARN symlink loop not followed`.
5. Summarise supported syntax, exclusions, unresolved references and audit results in `migration/depmap/report.md`.

## Languages without a bundled mapper: write an adapter

For a language with no bundled mapper (RPG, PL/I, Delphi, VB6, Perl...) or syntax the bundled one does not cover, the agent writes an **adapter** (a project-specific mapper). A dependency graph the agent guesses is not accepted. The **depmap-adapter skill** has the practical guide: choosing Python (copying a bundled mapper) or another language, which bundled mapper to start from, and how to build the fixture.

### Rules

- **Static only.** Read source files. Never build, run or test the original (in source-as-spec projects the original is assumed not to run).
- **Put it under `migration/tools/depmap-<language>/`.** Do not change the kit (`migration-kit/`).
- **Same output contract as the bundled mappers.** `edges.tsv` (header `from<TAB>to`), `order.txt`, `cycles.txt`, `unresolved.tsv` (header `file<TAB>reference<TAB>reason`), and `external.tsv` (header `namespace<TAB>files<TAB>first_file`) when it can tell external libraries apart; `/`-separated paths relative to `--root`, sorted.
- **Deterministic.** Walk files in sorted order; the same input gives the same output; nothing depends on randomness, time or parallel scheduling.
- **Avoid installs.** Prefer the Python standard library. If a compiler library (Roslyn, JavaParser...) is needed, ask the user first: it needs network access or an SDK.
- **Prefer extra edges to missing ones.** When in doubt add the edge; never drop a reference you cannot resolve, write it to `unresolved.tsv`.
- **List skipped directories at the top of the script** so generated output, build output and third-party code exclusions are visible.

### Steps

1. List the constructs that create dependencies in the language (file inclusion, module references, type names, calls, wiring in configuration files).
2. Write a small fixture under `migration/tools/depmap-<language>/fixture/` with a cycle, a skipped directory, fake references inside comments and strings, and a dynamic reference.
3. Write the expected `expected_edges.tsv` and friends **by hand**, then implement the adapter and compare.
4. Run the five-file trial on the real source and show it to the user (phase 01 rule).
5. Generate the whole map and record supported and unsupported syntax, exclusions and unresolved references in `depmap/report.md`.

After changing the adapter, regenerate the map and redo phase 01's checks (five-file trial, audits, and the dependency declaration from `make_review_dependencies.mjs`).

### When a bundled mapper fails or falls short

When a bundled mapper stops with an error, or cannot read the project's syntax (many `unresolved.tsv` rows with the same reason, obvious edges missing), do not stop the work. Handle it in this order:

1. **Try the options first.** `--include-var`, `--include-path`, `--copy-path`, the choice of `--root`, or a skipped-directory warning often explain it.
2. **Otherwise, copy the bundled mapper and fix the copy.** Copy the mapper and the shared parts it imports (whichever of `depmap_common.py`, `depmap_typed.py` and `depmap_projects.py` it needs) to `migration/tools/depmap-<language>/` and fix them there. Never change the kit's own files (`migration-kit/`). Before fixing, make the smallest example that fails as a fixture and write its expected output by hand (steps 2 and 3 above).
3. **Write it down in `depmap/report.md`:** the original error (or the syntax it could not read), what was changed, the fixture, and how the output differs from the bundled mapper's (edge, cycle and unresolved counts).
4. **Tell the user** in the phase 01 report that a fixed copy was used instead of the bundled mapper. When the fix rests on a guess (the language specification does not decide what the syntax means), ask the user before using it.

In every case, a dependency graph the agent guesses is not accepted.
