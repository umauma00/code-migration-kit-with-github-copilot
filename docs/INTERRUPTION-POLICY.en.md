# Work that is never cut short, and the conditions that still stop it

[日本語](INTERRUPTION-POLICY.md) | English

Normal execution is `executionMode: "continuous"`, including existing projects
without the key. Saved values such as `timeoutSeconds: 600` or `maxAgentCalls:
100` are not enforced. CPU use, elapsed time, call counts, fix rounds,
accumulated input and log volume never end work on their own. Transient
service or network failures are retried after a wait, and a running process is
waited for. The one exception: a worker call that writes nothing for
`workerSilenceSeconds` (600 s by default) is stopped and the same call retried,
to get out of a connection lost without an error; a call that keeps writing is
never stopped, however long it takes (table below).

Finite limits apply only when the person chooses `executionMode: "bounded"` or
passes `--max-calls N` / `--max-rounds N`. An agent must never add a finite
limit on its own. `concurrency` and the per-input model capacity still apply:
they split and queue work, they do not cancel it.

| Condition | Normal-run handling | Implementation |

| CPU at 100%, low CPU, a command, build or comparison with no output | Never terminated or restarted. No CPU-based exit exists; parent instructions forbid it | every harness skill, orchestrator, phase handoff |
| A worker call that writes nothing (since 0.44.0; `workerSilenceSeconds`, 600 s by default) | On 2026-11-02 (Windows, a company VPN, Cisco Secure Client, whose ISE Posture check often gets lost, and a network that drops while the screen is locked) one review call never returned and phase 04 stayed at 96 of 554 for 11 h 43 min. The CLI waits on a connection lost without an error (CLI 1.0.105 did not end a stalled answer on its own within 400 s, checked against a loopback provider). Workers now stream (`--stream on`: a line for each piece of text or reasoning that arrives) and the runner counts the time nothing arrives. After the set time it stops that call (with its child processes) and retries the same call after a short wait. It is not a deadline: a call that keeps writing is never stopped, and CPU is not looked at. Each retry doubles the wait (up to four times the setting: 10, 20, 40, 40, 40, 40 minutes by default), so a call that only thinks long without a word gets more room each time. Up to 5 retries per call, counted with the event stall, the lock wait, a network error next to the sign-in help, a connection taken over, and a call the CLI gave up on, a token check or a list of models it could not get, for a reason other than a network error, a rate limit or a 5xx (bounded mode: `transientRetries` caps the total). In translation a file that still gets nothing gets one more pass at the end of the run (like an answer slip; not in a repair run), then it and the files that use it stay unfinished; other files go on. Surveys retry each part the same way (no last pass). Time is counted from the last output in steps (a twentieth of the wait, at most 30 s), and a step that comes much later than planned (the computer slept, the runner was paused) counts as two, so a call that answers right after waking is not stopped. Output that came while the runner was busy is read and counted before the decision. Streamed lines are kept nowhere (memory, a log spilled to disk, a record), only how many came (`streamedDeltas`). The CLI version check before a call is watched with the same wait (a hung check is stopped, the call goes on with a warning). A process outside the call's tree (one that left the process group) that keeps the call's pipes open no longer keeps the call from ending: 5 s after the CLI is gone, killed or ended by itself, the runner lets them go (a call that ended by itself keeps its answer, with the check off too, and is not taken for a silent call or one past its deadline meanwhile). On Windows a taskkill that has not finished after 10 s no longer holds the call: the runner stops the CLI itself. Preparation audits (`audit_inputs.mjs run`, `run-pending`) retry the same way (no last pass), and Ctrl+C stops their worker CLIs with them. The review benchmark has no retry: a stopped call ends with the error, and running it again retries it. ## Conditions that still stop

These are not time or load cutoffs: continuing could not save a correct result.

| Kind | Examples |
|---|---|
| The person's action | SIGINT / SIGTERM / AbortSignal |
| Limits the person chose | bounded mode, explicit `--max-calls` / `--max-rounds` |
| Permission and phase scope | missing or stale approval, unfinished earlier phase, outside the approved batch or pilot |
| Input/output safety | writing over sources, protected paths, traversal, symlinks, duplicate targets, guardrail violations |
| Inputs changed during a run | source, rules, config, judge or repair intent changed |
| Concurrency and record integrity | a run/build-loop lock whose owner is alive or that comes from another host (an ownerless lock on this host is removed automatically), broken ledgers or hashes |
| Cannot start, sign-in, credits | missing CLI or runtime, unknown agent or model, expired sign-in, 403, service quota or billing limits (also GitHub's 402 Payment Required where the CLI loads the models and the CLI's "Copilot Pro trial paused", since 0.44.0 with the guidance `credits`) |
| Broken streams | corrupt JSONL or terminal events from the CLI itself, session errors (classified as above) |
| Preparation audit request over the input limit | `audit_inputs.mjs freeze` refuses instead of truncating; freeze again with fewer files per batch (or raise `maxReviewInputBytes`) |
| Required data that truly cannot be processed | binary files (NUL bytes that are not UTF-16), unreadable files, or required metadata (rulebook, one census site) larger than the model capacity on its own |
| Translation and test failures | non-zero typecheck, original, mutation, build, smoke or parity; fixable failures go to reviewed repair inside build-loop |
| No owner for a fix | a compiler diagnostic that maps to no manifest target, a failing original test, a defect in the judge itself |
| Real environment faults | ENOSPC, EACCES, EMFILE, EIO, spawn failure, OOM kill, external termination |
| Hooks cannot guarantee permissions | missing or invalid hooks, the host's 30 s hook limit (not a worker time limit) |
| Invalid helper input | unknown options, empty manifest, broken TSV or config |

Limits inside external services, the OS, VS Code or a project's own commands
cannot be lifted by the kit. A host wait API returning is not a process exit:
keep the run ID and wait. When an external stop happens, name its source and
exit code and resume from saved results.

The [source index](interruption-sources.json) and the regeneration and test
commands are described in the [Japanese page](INTERRUPTION-POLICY.md#再現可能な全ソース索引と検証).
