## 反映後の利用体験

`/code-migration` の親は工程と作業計画を示し、判断を要する点を利用者に提示する。
対応するホスト接続がある場合、仕事の起動・完成順回収・空き枠補充はコードが行う。
親が1件ずつ完了を待つ振る舞いによって、実装全体が逐次実行になる構造を解消する。
LLMの出力内容や完了順そのものの決定性を保証するものではない。

| 項目 | 反映後の動作 |
|---|---|
| 00〜06の10工程 | 既存の順序制御を使い、工程内の独立作業を並列化する。 |
| 04実装 | 実装済みAの2レビューを進めながら、独立したB/Cを実装する。完成した結果を直ちに提出する。 |
| レビュー | 同一固定候補への独立2レビューを並列にする。両方が揃ってから裁定・修正・完了へ進む。 |
| モデル | 要求値と実行情報を別に記録し、ホストの既知のID対応で照合する。指定不能・確認不能は理由を示す。 |
| 03試作 | 専用の使い捨て案件で限定した試作を実行し、結果を本番03の報告へ添える。 |
| 進捗 | 工程、稼働中の対象・役割、完了数、残件数、待ち・失敗理由を表示する。TODOが使えない場合はチャットへ表示する。 |
| 利用量 | main形式のcost-log.tsvを維持し、取得できた実績を記録する。未取得値はunknown。 |

本番の原本・RULEBOOK・judge・設定はrun中に固定し、対象の書き込みはrunnerに集約する。
同じ候補を変更しながら最終レビューを実行しない。依存先は既存の前提完了条件を守る。

## ホストごとの到達点

| 経路 | 反映する方法 | 完了を主張できる条件 |
|---|---|---|
| 現在のCLIバックエンド | 既存Node schedulerの並列処理を継続し、資料リンク・モデル記録・検証手順を修正する。 | CLIでプロファイル適用、モデル、JSON、レビュー、完了まで実際に確認する。現1.0.95環境では未確認。 |
| VS Code Copilot（Agent Host） | 対応するホスト接続からbackground起動・状態取得・結果取得・モデル情報取得を行い、nativeキューへ返す。 | 既存セッションへ接続できるAPIと必要な権限が確認され、実ホストで動作する。 |
| VS Code Local | 標準runSubagentの同一ターン並列呼び出しを具体化する。追加接続が使える場合に完成順回収・モデル情報取得を行う。 | 標準の同期呼び出しだけではbackgroundや完成順回収を保証しない。能力不足は開始前に表示する。 |

nativeで利用者が別途standalone Copilot CLIを導入しない方針は継続する。
VS Code Copilot内のSDK・同梱runtimeへの依存はある。
CLIバックエンドへ切り替える場合は利用者の実行方式の選択として扱う。

現在のMarkdownプラグインには、既存ホストセッションを操作する自動接続はない。
プロンプトにbackgroundを明記する段階でも改善は見込めるが、親AIの呼び出し判断への依存は残る。
コードによる制御には、対応するSDK接続・VS Code拡張等の実装と導入が必要になる可能性がある。
この追加接続の実現性・配布方法はまだ確定していない。

## 実装前に確認する接続契約

まずVS Code Copilotを対象に、最小限の接続を試作する。

1. 新しい別セッションではなく、利用者が起動した対象セッションへ接続できるか確認する。
2. 指定した専用agent・モデル・tools制限でbackgroundの仕事を起動できるか確認する。
3. agent ID/tool call ID、完了・失敗・取消、応答JSON、実際のモデル情報を取得できるか確認する。
4. それらをnative task ID、claim token、request hashへ結び付ける。
5. 実行モデルの確認と完成順submitを、親AIの自己申告や要求値の転記に依存せず行えるか確認する。

公開SDKやホスト内部に機能があることだけで、プラグインから接続できるとは判断しない。
非公開APIを安定した配布契約と推定しない。
接続できない場合は、指示の補強段階の対応として制約を表示し、nativeのコード制御が
完成したとは報告しない。モデル確認を必須にするnative経路は、取得不能なら開始前に止める。

## 接続できた場合の構成

親AIは計画、作業範囲の分割、質問、工程報告、Rubber Duck等の節目の助言を担当する。
ホスト接続は起動・結果回収・キャンセルと実モデル情報の取得を担当する。
Node runnerは依存関係、呼び出し上限、同時数、候補の反映、2レビューの合流、receiptを担当する。

Copilotの非同期起動には `mode: background` を使う。
LocalのrunSubagentへ存在しないmode引数を追加しない。
JS関数をasyncにすることや、各workerへ `--fleet` を追加することを解決策とは扱わない。

接続ループは、完了した結果を回収して即時submitし、新たなpendingを空き枠分だけclaim・起動する。
一群の全結果待ちをしない。起動済みの子との対応表はimmutable requestとは別に保持する。
モデル確認不能・不正JSON・起動失敗はfailとして提出する。
runnerが終了するまで接続を保持し、終了コードと現在のreceiptで完了を判定する。

同時数は実装・両レビュー・裁定・修正で共有し、ホストの許容範囲を守る。
現在の既定2を無条件に増やさない。実測と利用可能枠に基づく明示的な調整を可能にする。
Rubber Duckの追加助言は既存どおり工程境界で使い、必須2レビューの代わりにしない。

## 03のpilotで守る条件

本番の02と現在のjudgeを前提とし、03の試作実行を限定承認する。
試作先は本番出力と分離した使い捨て案件にする。
元案件、対象ファイル、入力のfingerprint、実行目的を記録し、許可範囲外の変換を拒否する。
既存の専用プロファイル・backend・モデル・独立2レビューを利用する。
pilotのreceiptを本番のtranslation完了記録として再利用しない。
試作報告をレビューして初めて本番03を完了し、その後に本番04を承認する。
本番のstrict制御を外して循環を回避する実装にはしない。

## 検証と作業順序

1. ホスト接続の最小試作で実現性を確認し、Copilot/Localの対応範囲と導入方法を確定する。
2. 接続ループ、モデル照合、doctorの能力判定を実装する。
3. コードによる実行と整合するように各skill/promptと進捗・利用量の表示を更新する。
4. pilot専用経路と資料リンクの不備を修正する。
5. 3つの模擬仕事で完成順回収・依存順序・同時枠・不一致拒否・古い結果拒否を確認する。
6. 対応ホストで小規模実行を行い、モデル、tools、JSON、独立2レビュー、完了、取消を確認する。

既存の並列化シミュレーションは、完成順回収の効果を示すもの。
実VS Code/実モデルの速度や、新しい接続が既に動くことの証明にはしない。
CLI 1.0.95の現環境では監視資源上限があり、別の正常な実行環境での確認が必要。
性能評価ではモデル処理時間、起動待ち、回収待ち、typecheck、依存待ちを分けて計測する。
