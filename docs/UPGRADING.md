## 0.46.0（末尾行の形・位置の誤りをキットが直す、末尾行だけの修正でレビューを保つ）

2026-11-04、Windows の工程 04（98/554）で、末尾行 PORT STATUS の誤り1つにかかる周回の重さが分かりました。まず答え直しでファイル全体をもう一度返させ、それでも誤っていれば確認済みの指摘 `marker:M1` として修正役がファイル全体をまた書き直し（その答えが誤っていればもう1回）、直したファイルはレビュー2人（指摘があれば裁定と修正も）を最初からやり直していました。末尾行はコードではありません。しかも誤りの多くは、判断の要らない形や位置の誤り（大文字や句読点、閉じないコメント、最後の閉じ括弧より前、同じ末尾行が2つ）です。

1. 末尾行の形や位置だけが誤っているときは、ランナーが AI を呼ばずに書き直します。条件は4つです。PORT STATUS の行がどれも行全体のコメントであること（`PORT STATUS:` の直前がコメントの開始記号。閉じないブロックコメントは、その下に閉じ記号だけの行しかないときに限る）、確信度と件数がどれも同じであること（順序、大文字、`=`・`:`・空白、`todo` と `todos`、値や全体を囲む引用符や括弧、間のカンマは問いません。対になる相手のない引用符・バッククォート・括弧が残る行は、上で開いた文字列を閉じる行かもしれないので読みません）、件数が `TODO(port)` の行数と合うこと、最初の末尾行より後の空でない行がどれもブロックを閉じる行であることです。閉じる行は、閉じ括弧（波・角・丸）、`end`・`endif`・`end;`・`End Class` などの終わりのキーワード（`endef`、裸の `END`・`End`、`end_time` のような語は除く）、`#` のコメントの下の `fi`・`done`・`esac`、`#endif`・`#endregion` で、後ろに1行コメントがあっても構いません。XML などのマークアップのコメント（`<!--`・`<%--`・`<%#`・`{#`）は閉じタグと HTML コメントの下へだけ動かし（Razor の `@*` は両方）、`</pre>`・`</textarea>`・`</script>` など中身を書いたとおりに扱う要素の終わりの下へは動かしません。1行コメントの末尾行は同じ種類の1行コメントの下へも動かします。引用符やバッククォートを含む行（VB の `'` はコメント）、ブロックコメントや長い文字列を閉じる行（`-->`・`*/`・`*)`・`#>`・`]]`・`-}`・`%}` など）、上で開いたヒアドキュメントの終わりの語で始まる行（`<<<END` … `END;`、`<<~end`）、末尾行へ行末のバックスラッシュで続く行があれば、その先へは動かしません。YAML では動かさず、Razor・MDX・Astro・Svelte ではコードの下へ動かさず（コードブロックの後はページの文字になるため）、Ruby・Perl・Elixir・Crystal・Pascal では括弧を含む行の下へ動かしません（括弧が `%w[ ]`・`qw( )`・`{ }` コメントの終わりかもしれないため）。YAML と Markdown では字下げした末尾行に触れません。書き直しはコメントの開始記号を保ち（構文はワーカーが選んだもの）、足りない閉じ記号を足し、`<開始記号> PORT STATUS: confidence=<c> todos=<n>`（と閉じ記号）を最後の空でない行の後に置きます。改行の種類（CRLF・LF）、ファイルの最後の改行（またはその無いこと）、BOM は保ちます。JSON の仲間は末尾行のコメントを取り除きます（`TODO(port)` の書き込みがあるものは除く）。書き直した結果が検査に通り、末尾行のほかに何も変わっていないときだけ使います。
2. 次はこれまでどおりワーカーが直します。`TODO(port)` の行数と食い違う件数（`TODO(port)` の行の書き忘れかもしれません）、末尾行がない（確信度はワーカーが決めるもの）、食い違う末尾行、値のほかの言葉、コードと同じ行の末尾行、閉じる行ではない行（コード、文字列の終わり、PHP の `?>`、`//` コメントの下の `</script>`）や、1. で動かさないとした行より前の末尾行、行末のバックスラッシュで続く1行コメント、レビューの段階で UTF-8 と読まれないファイル（書き直すと文字コードが変わるため）。
3. 実装役と修正役の答えは書き込む前に書き直し、答え直しの判定も書き直した結果で行うので、ランナーが直せる末尾行では答え直しが起きません。書かれたファイルは、修正役に回す代わりに、レビュー・修正・完了の各段階でその場で書き直し、レビューは書き直したファイルを見ます。ワーカーの記録には答えたままの内容が残ります。書き直すたびに「trailer rewritten by the runner」と表示し、実行の要約の `selfRepairs.markerRewrites` に数えます。
4. single-pass（`fixPolicy: "single-pass"`、新規導入の既定）の修正の後に末尾行が誤っていて修正役に回したとき、修正役が末尾行のほかに何も変えなければ、その修正のレビュー2人と記録を保ちます（末尾行が検査に通れば「trailer fixed alone; the single-pass reviews stand」と表示し、`selfRepairs.reviewsKept` に数えます。まだ誤っていればレビューを保ったまま修正役に戻し、1回の実行で2回直しても誤っていて止まった単位は、次の実行でレビューを保ったまま修正から始めます）。single-pass の修正の後はもともとレビューしないうえ、末尾行はコードではないためです。件数を合わせるために `TODO(port)` の行を足したなど、ほかも変えた修正と、single-pass の修正を元に戻した修正は、これまでどおりレビューします。`fixPolicy: "rereview"` のとき（途中で切り替えて再開したときも含む）と、型検査だけの修正の後の末尾行の修正も、これまでどおりです。単位ごとの `typecheck` があれば、先にもう一度実行します。ランナーが書き直した末尾行も、single-pass の修正の後ならレビューを保ち、ほかのレビュー済みのファイルではレビューし直します。
5. single-pass の記録（`singlePass`）に、修正の後に末尾行を直したことを示す `trailerFixedBy`（ランナーなら `runner`、修正役なら `fixer`）が加わります。このときの完了判定は、修正役の記録の内容と今のファイルの違いが、行全体の PORT STATUS コメント（とその前の最後の改行の有無）だけであることを確かめます。末尾行そのものは、これまでどおり検査に通る必要があります。
6. 記録の形は `singlePass.trailerFixedBy` が加わるだけで、プロンプト、RULEBOOK のテンプレート、末尾行の決まりは変わりません。0.45.1 から上げると、承認、完了記録、工程の記録、準備した事前試行、完了した単位はそのまま保たれます（それより前の版からは、間の版の注意も見てください）。工程 04 の途中でも入れられます。ランナーを止め（Copilot アプリでは実行中のコマンドの Stop）、更新して、同じフォルダーで `translate` をもう一度実行すると、未完了の単位から続けます。修正役に回る途中で止まっていた単位や、single-pass の修正の後に `verify-fix` で止まっていた単位（単位ごとの `typecheck` があるとき）は、ランナーが直せる末尾行なら呼び出しなしで先へ進みます。以前のキットが `done` の段階で完了できずに残した単位は、これまでどおりレビューからやり直します。
7. `trailerFixedBy` の付いた完了した単位は、0.45.x 以前のキットからは未完了に見え（修正役の内容とファイルが一致しないため）、レビューからやり直されます。複数のホスト（別の PC、VS Code、CLI）で同じ案件を進めるときは、すべてのホストを 0.46.0 にそろえてから実行してください。
8. コピー導入では `migration-kit/` 全体と `.github/skills/` の SKILL.md を一時導入の内容で置き換えます（オーケストレーターの指示は変わらないので、承認は保たれます）。プラグイン導入は更新だけで入ります。

## 0.45.1（XML など1行コメントのない形式の末尾行・JSON ファイル）

2026-11-04、Windows の工程 04（98/554）で、Database.xml が実行のたびに修正役へ差し戻され、未完了のまま残りました。`markerPolicy` `todo-lines-v1` の末尾行は `todos=` の数の直後で行が終わる決まりでしたが、XML には1行コメントがありません。正しい XML のまま書ける `<!-- PORT STATUS: confidence=medium todos=2 -->` は不合格になり、合格するのは閉じないコメントや裸の行など、XML として壊れたファイルだけでした。1回の実行で、ファイル全体を書き直す修正役の呼び出しが最大4回（差し戻し2回、それぞれに答え直し1回）かかってから未完了になり、次の実行でも同じことを繰り返していました。HTML・JSP・CSS など、1行コメントのない形式はどれも同じです。コメントを書けない JSON は、どう書いても壊れたファイルになりました。

1. 末尾行の数のあとに、その行で閉じるコメントの閉じ記号を置けるようになりました。閉じ記号は `-->`・`--%>`・`%>`・`*/`・`*@`・`#}`・`*)` の7つだけです。XML や HTML は最後の閉じタグの後に `<!-- PORT STATUS: confidence=medium todos=2 -->`、JSP は `<%-- PORT STATUS: confidence=medium todos=2 --%>`、CSS は `/* PORT STATUS: confidence=medium todos=2 */` と書けば通ります。Handlebars などの HTML のテンプレートも `<!-- -->` で書きます（`--}}` などテンプレート独自の閉じ記号は通りません）。上の行で `<!--` を開き、末尾行の最後を `-->` で閉じる形も通ります。`}` や `)` など、コードの閉じ括弧はこれまでどおり通りません（末尾行がコードの中にあることになるため）。
2. 末尾行で `PORT STATUS:` の直前に開いたコメント（`<!--`・`<%--`・`<%#`・`/*`・`{#`・`@*`・`(*`）は、同じ行のその閉じ記号で閉じます。0.45.0 が通していた `<!-- PORT STATUS: confidence=medium todos=2`（`-->` なし）は、ファイルの最後でコメントが閉じず XML として壊れるので、新しい答えと、まだ完了していない単位では誤りとし、行の最後に `-->` を足すよう伝えます（完了済みの単位は下の 4 のとおり完了のままです）。
3. JSON の仲間（`.json`・`.jsonl`・`.ndjson`・`.geojson`・`.topojson`・`.jsonld`・`.webmanifest`・`.ipynb`・`.har`・`.sarif`・`.gltf`、大文字小文字は問いません）はコメントを書けないので、末尾行なしで完了します。末尾行を書いた答えは、取り除くよう答え直させ、書かれたファイルに残っていれば確認済みの指摘 `marker:M1` として修正役に回します。既存の RULEBOOK はすべてのファイルに末尾行を求めているので、JSON ファイルの最初の答えに末尾行が付き、答え直しが1回かかることがあります。CSV・TSV など、JSON 以外のコメントのない形式は対象外で、これまでどおり末尾行が要ります。
4. 完了済みの単位は失効しません。0.45.0 以前に末尾行つきで完了した JSON ファイルも、閉じないコメント（`-->` のない `<!-- PORT STATUS: ...`）や裸の行（`PORT STATUS: ...` だけの行）の末尾行で完了した XML・HTML・JSP・CSS なども、ファイルを書き換えない限り完了のままです。ただし、これらは JSON や XML として読むと誤りになります（裸の行は、今の版もコメントでない行と見分けられないので、新しい答えでも通ります）。次のように探して、手で直してください。
   - `migration/` の下は書き換えないでください。キットの記録で、作業役の答えの写しにも末尾行が入っています。書き換えると、完了済みの単位がレビューし直しになります。
   - プロジェクトのフォルダーで次の2つを実行します（git で管理していないフォルダーでも動きます。PowerShell・cmd・bash（Git Bash を含む）・zsh のどれにもそのまま貼り付けられます）。1つ目は JSON の末尾行を、2つ目は閉じないコメント（行の途中で開いたものも）と裸の行を、どの形式でも1つ上の行と一緒に出します。2つ目の `<.--` と `<.#` は `<!--`・`<%--`・`<%#` に当たります（`!` は bash・zsh で、`%` はバッチファイルで別の意味になるので書いていません）。

     ```
     git -c core.quotepath=off grep --no-index -n "PORT STATUS:" -- ":(icase)*.json" ":(icase)*.jsonl" ":(icase)*.ndjson" ":(icase)*.geojson" ":(icase)*.topojson" ":(icase)*.jsonld" ":(icase)*.webmanifest" ":(icase)*.ipynb" ":(icase)*.har" ":(icase)*.sarif" ":(icase)*.gltf" ":(exclude)migration" ":(exclude)migration-kit"
     git -c core.quotepath=off grep --no-index -n -B 1 -E "(^|<.--|<.#|/[*]+|[{]#|@[*]|[(][*]+)[[:space:]]*PORT STATUS:.*[]0-9][[:space:]]*$" -- ":(exclude)migration" ":(exclude)migration-kit"
     ```

   - 直すのは、変換で作ったファイル（manifest の変換先）だけです。`bin/`・`obj/`・`dist/`・`node_modules/` などにあるビルドの写しは、元のファイルを直してビルドし直せば変わります。
   - JSON は、その行を消します。末尾行がコメントを開いていれば（`<!--`・`<%--`・`/*` など）、行の最後にその閉じ記号（` -->`・` --%>`・` */` など）を足します。裸の行は、上で開いたコメントの中にあれば（1つ上の行が `<!--` のときなど。開き記号がもっと上にあることもあるので、ファイルで確かめてください）行の最後にその閉じ記号を足し、そうでなければ `<!-- ... -->` で囲みます（JSP は `<%-- ... --%>`、CSS は `/* ... */`。1行コメントのある形式なら、`// ` などを行の前に付けます）。
   - git がなければ、エディターで `PORT STATUS:` を検索して同じように直します（`migration/` と `migration-kit/` の下は除きます）。
   - 直したファイルは、ほかの書き換えと同じく、次の `translate` で一度だけレビューし直します（変換し直しはしません）。JSON の末尾行と閉じないコメントは、直さずにおくと、後で別の理由（RULEBOOK の変更など）でレビューし直しになったときに、修正役がファイル全体を書き直して直すことになります。
5. 末尾行の修正（`marker:M1` だけの修正）は、修正役を呼ぶ前にファイルを確かめ直します。以前の版で修正の途中に止めたファイルは、末尾行が今の決まりで通れば、修正役を呼ばずにレビューへ進みます。通らなければ、以前の版の言い方ではなく、今の版が見つけた誤りを修正役に伝えます（以前の版の言い方「does not read ...」は、XML のコメントでは満たせませんでした）。
6. 1回の実行で末尾行の修正を2回しても通らず、未完了になったファイル（Windows の Database.xml はこれと見られます）は、次の `translate` で、レビューの前にまず末尾行を確かめます。今の決まりで通れば（閉じたコメントなど）、修正役を呼ばずにレビュー2回へ進みます。通らなければ、今の版の言い方で修正役に回します（1回の実行で2回まで）。
7. 末尾行の誤りの説明に、コメントを次の行で閉じた場合（`<!--` の次の行に末尾行、その次に `-->`）と、末尾行で開いたコメントを閉じていない場合の直し方を加えました。
8. 作業役（変換役・修正役）への指示に、1行コメントのない形式の書き方と使える閉じ記号、JSON の扱い（拡張子の一覧つき）を加えました。レビュアー2人と arbiter には、この2つの形を欠陥として扱わないよう伝えます。修正が印（`TODO(port)` の行と末尾行）だけを変えたかを見る処理も、JSP・ERB・Razor・Jinja・OCaml のコメントに書いた印を印として扱います。JSON ファイルの修正役には「末尾行に数える」と言いません。
9. 新規導入の RULEBOOK のひな形（英日）に同じ書き方を加えました。既存の `migration/RULEBOOK.md` は書き換えず、書き換える必要もありません（書き方はキットが作業役に伝えます）。04 の途中で RULEBOOK を変えると、受け入れ（`rulebook accept`）をしない限り完了済みがすべてレビューし直しになるので、変えないでください。
10. 記録の形は、JSON ファイルの新しい記録に `noTrailer: true` が加わるほかは変わりません。0.45.0 までに通った末尾行は、記録する項目も値もこれまでと同じなので、0.40.1 以降からの更新では承認・完了記録・工程の記録・準備済みの試運転・終わった単位は失効しません（0.40.0 からは 0.40.1 の項のとおり）。工程 04 の途中でも入れられます。runner を止めて（Copilot app では実行中のコマンドの Stop）更新し、同じフォルダーで `translate` をもう一度実行すると、終わっていない単位から続けます。
11. この版で新しく完了できるようになったファイル（閉じるコメントの末尾行、末尾行のない JSON）は、0.45.0 以前のキットでは未完了に見え、修正役へ差し戻されます。同じプロジェクトを複数のホスト（別の PC、VS Code と CLI など）で動かすときは、すべてのホストのキットを 0.45.1 に揃えてから動かしてください。
12. コピー導入では `migration-kit/` 全体を一時導入先の内容に置き換えます（オーケストレーターの指示とスキルは変えていないので、承認は失効しません）。プラグインは更新だけで入ります。

## 0.45.0（設定を変えるファイルは settings.json だけ・設定を変えたときのやり直しを狭める）

2026-11-02、「run-settings と config の違いは？紛らわしいので1つで良くないか」という指摘から。`migration/` に設定らしいファイルが3つ（`run-settings.json`・`config.json`・`preferences.json`）並び、どれを変えればよいか分かりにくくなっていました。さらに、モデルやコマンドなど、どの設定を変えても完了済みの単位がすべてレビューし直しになっていました。

1. 設定を変えるファイルは `migration/settings.json` だけになりました。次に作業をするキットのコマンド（`status`・`phase next` など読むだけのものを除く）を始めたときに、`migration/run-settings.json`（と `run-settings.help.md`）の名前が `settings.json`（と `settings.help.md`）に変わります。書いた値はそのままです。説明（`_about`）や説明ファイルが古い名前を指していれば、書き直します（このときは Copilot CLI を起動しないので、説明ファイルにモデルの一覧は入りません。一覧は `models` で確かめられ、`settings init` で一覧つきに書き直せます）。
2. 同じときに、キット自身の記録 `migration/config.json` と `migration/preferences.json` が `migration/state/` へ移ります。名前を変えるだけで中身は変えないので、それまでの承認・完了記録・工程の記録・準備済みの試運転はそのまま有効です。別のコマンドが実行中なら、移動は次のコマンドまで待ちます（その間も元の場所のまま読みます）。読めない（壊れた）記録は移さず、`status` がその場所を示すので、そこで直してください（バージョン管理から戻すなど）。
3. ファイルを書き換えたら、`settings apply` を待たなくても、次にキットのコマンドを始めたときに全項目を確かめて反映します。誤りがあれば何も書き込まず、そのコマンドの出力と `status` に誤りを全部示します（項目名の書き間違いも示します）。チャットで変えた値（`models set`・`preferences` など）や、キットの記録を手で書き換えた値は、ファイルに写します（元に戻しません）。両方で変えたときはファイルの値を使い、そう伝えます。モデルを変えたときは、アカウントのモデル一覧で確かめてから反映します（サインインが要ります）。一覧は最大1分待ち、読めなければその変更だけを次のコマンドに回して、コマンドはそのまま進みます。自動モードへの切り替えだけは、これまでどおり `settings apply` で反映します（確認が出ます）。
4. 設定を変えたときのやり直しを、その設定が影響する作業だけに狭めました（[変えたときにやり直しになるもの](REFERENCE.md#変えたときにやり直しになるもの)、`settings.help.md` にも同じ説明）。

   |---|---|---|
   | モデル・エフォート・コンテキスト、レビューの進め方（`fixPolicy`・`reviewFocus`・`dependencyOrder`・`maxReviewInputBytes`）、単位ごとの `typecheck`、案件側のエージェント・hook | 完了済みの単位をすべてレビューし直し、承認と工程02以降の記録も取り直し | 何もやり直さない（これからの作業に使う） |

   コマンドに書いたファイル（ビルドのスクリプトなど）を変えたときは、そのコマンドを変えたのと同じです。source-only の案件は `original`・`mutation`・`parity` のどのコマンドも実行しないので、変えても何もやり直しません。`buildArtifactRoots` だけを変えたときは、工程 00〜02 の記録はそのままで、03 だけを judge の後に記録し直します。コマンドを書き換えたときなどに出る説明（`note`）も、何がやり直しになるかを言うようになりました。
5. 0.44.x で作った記録は、更新しただけでは失効しません。最初に実行したキットのコマンド（`status`・`phase next` など読むだけのものを除く。`models set`・`settings apply`・`preferences` も含む）が、設定を変える前に、古い記録が何を表していたかを `migration/state/context-upgrade.json` に一度だけ書き留め、その後は 0.45.0 の記録と同じく、影響する設定を変えたときだけやり直しになります（たとえば更新の後にモデルを変えても残ります）。そのとき読めない入力があれば（ファイルがないなど）、その時点のキットの記録を残しておき、読めるようになったときにそれをもとに書き留めるので、その間に変えた設定も、書き留めた後と同じく、影響する作業だけをやり直しにします（モデルを変えても古い記録は残ります）。このファイルはキットだけが書き、エージェントが書き換えようとするとフックが止めます。更新の時点ですでに古くなっていた記録は、設定やファイルを元に戻しても古いままです。そのまま記録し直してください。
6. どこか1台で 0.45.0 を動かす前に、この案件で使うすべてのホスト（別の PC、VS Code と CLI など）のキットを 0.45.0 にしてください。記録を移した後の 0.44.x 以前のキットは、移した記録を見つけられません。そのホストではフックが何も確かめなくなり（禁止リスト、言語の確認、自動モードへの切り替えの確認も止まります）、コマンドは「初期化されていない」と言って止まります。初期化し直さず、そのホストのキットを更新してください（記録を移したコマンドも、その出力でこう伝えます）。0.44.x のキットが動くと古い場所に記録を書き直すこともありますが、新しい場所に記録があるとき、古い場所のファイルは使わず、コマンドの出力と `status` が「使われていません」と示します。全ホストを 0.45.0 にそろえてから消してください。
7. コピー導入では `migration-kit/` 全体を一時導入先の内容に置き換え、`.github/` を置き換える前に、`node migration-kit/scripts/run_migration.mjs doctor` を1回実行してください（`status` や `models` の一覧など、読むだけ・一覧を出すだけのコマンドでは書き留めません）。0.44.x の記録は案件側の `.github/agents/`・`.github/hooks/` も材料に入れていたので、先に置き換えると、古い記録の意味を書き留める前に材料が変わります。先に置き換えてしまっても、工程 02 か 03 の記録があれば、そこから古い記録の意味を確かめられるので失効しません（工程の記録がない `phasePolicy: legacy` の案件では失効します）。プラグインは更新だけで入ります。
8. 残る制限：移行元のファイルは全体で1つとして扱うので、1ファイルを変えても完了済みの単位はすべてレビューし直しになります（0.44.x と同じ）。

## 0.44.0（反応のない AI の呼び出しを止めてやり直す）

2026-11-02、Windows（キット 0.42.0、Copilot アプリ、会社の VPN）の工程 04 が、96/554 のまま11時間43分止まっていました。レビューの呼び出し1回が戻らなかったためです。PC はスリープしていませんでしたが、画面をロックしてしばらくすると通信が途切れ、VPN の確認（Cisco Secure Client の ISE Posture）もよく迷子になる環境でした。こうして切れた接続では CLI にエラーが届きません。Copilot CLI 1.0.105 は、止まった応答を少なくとも400秒は自分で打ち切りませんでした（127.0.0.1 の偽プロバイダで確認。`COPILOT_NATIVE_HTTP_TIMEOUT_MS` を設定しても同じ）。通常モードの runner には時間の上限がなく、オーケストレーターも止めないので、実行はその1回をずっと待っていました。

1. 作業役の CLI に途中経過を出させます（`--stream on`。これまでは `off`）。JSON 出力のまま、文章や考え中の内容が届くたびに `assistant.message_delta`・`assistant.reasoning_delta` の行が出て、最後にこれまでどおり全文の `assistant.message` が出ます（キットが読むのはこれです）。ストリームで答えないプロバイダでもこれまでどおり動きます（どちらも偽プロバイダで確認）。
2. 作業役の呼び出しが `workerSilenceSeconds`（新設、既定600秒）のあいだ何も出力しなければ（標準出力にも標準エラーにも）、その呼び出しを子プロセスごと止め（「Process showed no sign of progress for 600s …」）、少し待ってから新しい CLI セッションで同じ呼び出しをやり直します。期限ではなく、CPU も見ません。出力が続く呼び出しは、どれだけ長くかかっても止めません。やり直すたびに待つ時間を倍にします（最大で設定の4倍。既定では10・20・40・40・40・40分）。途中経過を出さずに長く考えるだけの呼び出しにも、やり直すたびに時間を与えるためです。呼び出しの前の CLI のバージョン確認（`--version`）も同じ時間で見張ります。何も出さずに止まったら止めて、呼び出しは「Copilot CLI version unknown before this call」の警告つきで続けます（これまでは、すべての呼び出しがその確認を待ち続けました）。呼び出しのプロセスの外のもの（プロセスグループを抜けたものなど）が出力の通り道（パイプ）を持ち続けても、CLI が止められるか自分で終わってから5秒後に手放すので、呼び出しが終わらないままにはなりません（自分で終わった呼び出しは答えをそのまま使います。見張りをやめていても同じです。その5秒の間に、無反応や期限切れとして扱うこともありません）。ビルドや比較のコマンドも同じです。macOS と Linux では、自分で終わったコマンドが残したものが出力をつかんだままなら（スモークテストのコマンドがバックグラウンドで起動して止めなかったサーバーなど）、そのコマンドのプロセスグループに残ったものを、期限切れのときと同じように先に止めます。出力をつかんだままのものがなければ、残したものは動き続けます。Windows ではいつも動き続けるので、コマンドは自分で起動したものを止めるようにします。Windows で taskkill が10秒たっても終わらないときは、CLI 自体を止めて先へ進みます。
3. 無反応のやり直しは1回の呼び出しにつき5回まで（既定で合計約190分）で、CLI の受け渡し待ち・ロック待ち・サインインの案内つきの通信エラー・途中で引き取られた接続（下の8）、それに、通信エラー・レート制限・5xx 以外の理由で CLI があきらめた呼び出し（下の7）や、CLI がトークンを確かめられなかった・モデルの一覧を取れなかったとき（下の9）と合わせて数えます。bounded モードでは、これまでどおり `transientRetries` が全体の上限です。それでも反応がないファイルは、それを使うファイルとともに未完了にして、ほかのファイルは進めます。調査は区切りごとに同じくやり直します。レビューのベンチマークにはやり直しがないので、止まった呼び出しはエラーで終わり、もう一度実行するとやり直せます。
4. 変換（工程 04）では、一時的な失敗でやり直しを使い切って未完了になったファイル（無反応、受け渡し待ち・ロック待ち、CLI があきらめた呼び出し、CLI がトークンを確かめられなかった・モデルの一覧を取れなかったとき、引き取られた接続、サインインの案内つきの通信エラー。bounded モードでは一時的な失敗すべて）を、答えの書き損じと同じく、実行の最後にもう1周やり直します（進み具合に「one more pass for N unit(s) blocked by a call that showed no sign of progress」または「… by a temporary failure」）。その間に通信が戻っていれば、人の手なしで終わります。修正の実行（repair）と、呼び出しの上限（`maxAgentCalls`・`--max-calls`）を使い切った実行ではしません（やり直しを待つ間に使い切ったときも）。調査と準備監査に最後のもう1周はありません。
5. 準備監査（`audit_inputs.mjs run`・`run-pending`）も、変換と同じく一時的な失敗をやり直します。無反応・レート制限・5xx・通信エラーなら、依頼が今も有効でまだ提出されていないことを確かめてから、少し待って新しいセッションで同じ依頼をやり直します。これまではすぐに失敗していました（無反応ならずっと待っていました）。一時的でない失敗や、実行全体を止める失敗は、これまでどおりすぐに終わります。Ctrl+C で止めると、作業役の CLI も一緒に止めます（これまでは CLI が残って動き続けました）。
6. 次の通信エラーも、すぐにファイルを未完了にせずやり直します。名前が引けない（ENOTFOUND、getaddrinfo、「dns error」「failed to lookup address」「No such host is known」、os error 11001・11002）、ネットワークやホストに届かない（ENETUNREACH、ENETDOWN、EHOSTUNREACH、EHOSTDOWN、「network is unreachable」「host is unreachable」「host is down」「no route to host」）、この PC が接続を切った・リセットされた・拒否された（ECONNABORTED、「connection refused」「connection reset by peer」「forcibly closed by the remote host」「connected party did not properly respond」「target machine actively refused」「established connection was aborted」、os error 10050〜10054・10060・10061・10064・10065）、答えの途中で切れた（「error reading a body from connection」「error writing a body to connection」「end of file before message length reached」「connection closed before message completed」）、undici のソケットとタイムアウトのコードです。CLI の通信部分の接続の時間切れ（「connect-stage timed out」「connect error: deadline has elapsed」）、終わりの合図（close_notify）なしで閉じた TLS や、つなぐ途中で切れた TLS（「tls handshake eof」）、プロキシのトンネルの入出力エラーと時間切れ（「proxy CONNECT I/O error」「tunnel I/O error」「proxy CONNECT did not complete within」）、組織の IP 許可リストによる拒否（「IP allow list enabled」「IP address is not permitted」。VPN が切れて社外からの接続になったとき）も同じです。VPN のつなぎ直しや PC の再確認、眠った通信が残すエラーです。ETIMEDOUT と同じく、通常モードでは回数の上限なくやり直します。CLI のサインインの案内がついているときは、これまでどおり5回までです（CLI がトークンを確かめられなかった・モデルの一覧を取れなかったと書いたときを除く。下の9）。CLI の通信部分が外側につける「error sending request」だけでは通信エラーとみなしません（証明書・トンネルを断るプロキシ・誤ったアドレスも同じ形で来るため。AI の呼び出しでプロキシに断られたトンネルは、CLI があきらめた呼び出し（下の7）として来ます）。
7. CLI が自分で何度かやり直してあきらめた呼び出し（「Failed to get response from the AI model; retried N times … Last error: …」、または「… because the slow-stream retry limit was reached」）もやり直します。最後のエラーが通信エラー・レート制限・5xx なら、それと同じく回数の上限なく、それ以外（答えの終わりが来なかった、JSON でない返事など）は5回までです。これまでは、最後のエラーがキットの知っている一時的な失敗でなければ、ファイルをすぐ未完了にしていました。2026-11-02 に実物の CLI で、答えの途中で切れた接続がこの形（「error reading a body from connection: unexpected EOF during chunk size line」）で来ることを確かめました。
8. 接続が途中で引き取られたときは、5回までやり直し、回数の上限なくやり直すことはしません。このパソコンが信頼していない証明書（UnknownIssuer・NotValidForName・certificate verify failed・自己署名など）、「does not appear to originate from GitHub」、CLI がトークンを確かめる段階で GitHub の形ではない返事が来たとき（4xx の「Failed to fetch PAT user login (403): Failed to fetch Copilot user info: 403 Forbidden: <html>…」や、200 で来たページの「Invalid Copilot user response」）、CLI がモデルの一覧を取る段階で GitHub の要求 ID がない返事や 200 で来たページが来たとき（CLI 自身の行で「(Request ID: …)」のない「Error: Access denied by policy settings」、「Error: expected value at line 1 column 1」）、プロキシが通信の中で自分へのサインインを求めたときと、CLI がそのサインインをできなかったとき（「407 Proxy Authentication Required」、モデルの一覧を取る段階では「Error: 407」。Kerberos の「proxy Negotiate authentication failed: failed to acquire proxy credentials: …」、「tunnel error: proxy authorization required」）、ネットワークが自分のページでサインインを求めたとき（ポータルの「511 Network Authentication Required」、モデルの一覧を取る段階では「Error: 511」）です。どれも `copilot login` では直りません。0.43.1 までは、Negotiate の失敗と 511 のページはサインインの問題として実行を止めていました。会社のプロキシ・VPN・セキュリティソフトが暗号化された通信の中身を確かめていると、設定を直すまで通らないためです。VPN の確認中（ISE Posture など）に一時的に起きることもあるので、すぐには未完了にしません。案内 `cli-intercepted` は、つながってからのやり直し（プロキシのサインインなら、パソコンのロックを解除し、VPN がつながっているのを確かめてから）と、会社の証明書を `NODE_EXTRA_CA_CERTS` で CLI に教えること、プロキシがサインインを求め続けるなら管理者にプロキシの設定を確かめてもらうことを示します。ただし CLI がトークンを確かめる段階では、それ以外は CLI が原因を書きません（証明書も、断られたプロキシも、名前の引けないプロキシも「network fetch failed: request failed: error sending request for url (…)」になります）。VPN が切れているのと見分けられないので、そこでは通信エラーとして回数の上限なくやり直します（`status` が、30分を超えて続いていることを示します）。
9. CLI がサインインのトークンを確かめられなかったと書いたとき（「Authentication token found but could not be validated … Your token may still be valid. Check your network connection」）と、起動時に使えるモデルの一覧を取れなかったと書いたとき（「Error: Failed to load models … Copilot could not retrieve the list of available models.」）は、サインインの問題とみなしません。作業役の呼び出しはどれも、起動時にモデルの一覧を取りに行きます。CLI 1.0.105 は通ったトークンの確認の結果を覚えておくので、VPN が切れると、まずここに出ます（届かなくなった会社のプロキシ、プロキシに断られた・閉じられたトンネルなど）。通信エラー・レート制限（429、またはトークンの確認で「rate limit」と書いた 403）・5xx が一緒なら、回数の上限なくやり直します（0.43.1 までは、通信エラーが一緒ならサインインの疑いとして5回まで、ほかは実行を止めていました）。ほかのエラーなら5回までやり直します。作業役を自分の CLI の置き場所へ移すこともしません。ただし GitHub がトークンの確認に答えて、GitHub のエラーの形で断ったとき（「Failed to fetch PAT user login (403): GitHub returned: …」のように、レート制限以外の 4xx。トークンに権限がない、SAML の承認がない、Copilot が有効でないなど）は、これまでどおりサインインの問題として実行を止めます（`workerCopilotHome` が "separate" なら、先に自分の CLI の置き場所でもう一度試します）。モデルの一覧を GitHub が断ったときは別の言葉で出て、これまでどおりに扱います。401（「Authentication failed」）は実行を止め、403（「Access denied by policy settings (Request ID: …)」）はそのファイルを未完了にし、402（「Error: 402 Payment Required」。AI Credits・予算・プランの問題）は実行を止めます。402 の案内は、サインインではなく `credits`（課金・予算・プランの確認）になりました。CLI が「Error: Copilot Pro trial paused」と書いたとき（試用の一時停止）も、同じ案内で実行を止めます（0.43.1 までは、ファイルを1つずつ未完了にしていました）。403 と同じ言葉でも GitHub の要求 ID がなければプロキシの画面です（GitHub の 403 を要求 ID を外して伝えるプロキシでは、そのファイルを未完了にする前に5回のやり直しと最後の1周をします）。そこでの 407・511・200 で来たページも、プロキシやポータルのものです。どれも途中で引き取られた接続（上の8）です。組織の IP 許可リストによる拒否は通信エラー（上の6）、トークンの確認でのほかの形の 4xx の返事は途中で引き取られた接続（上の8）です。ただし 401 の返事と、前に「Proxy」も「Network」もなく「Authentication Required」と書いた返事は、サインインの問題として実行を止めます。
10. 無反応の時間は、最後の出力から区切り（設定の20分の1、最大30秒）ごとに数えます。予定よりずっと遅れて来た区切り（スリープ、runner が忙しかった・一時停止していた）は2区切りとしか数えず、その間に届いていた出力も止めるかどうかを決める前に読むので、PC が目覚めた直後に答える呼び出しは止めません。
11. `workerSilenceSeconds` は 0（見張りをやめる。作業役は途中経過を出さず、0.43.1 までと同じく呼び出しが戻るまで待ちます）か、300〜86400 の整数です。300 秒より短くできないのは、CLI がレート制限の待ち（Retry-After。180秒まで）を何も出さずに待つためです。実行の設定なので、変えても承認やレビュー済みの作業は失効しません。
12. `status` は、無反応でやり直している呼び出しを「a call that showed no sign of progress, most likely a connection lost without an error」と示し、runner は止めずに PC の接続を保つよう案内します。通信エラーでやり直しているときは VPN・プロキシの設定（HTTPS_PROXY・NO_PROXY）・会社の証明書（NODE_EXTRA_CA_CERTS）の確認を勧め、30分を超えると「the longest for about N minutes」と続いている時間も示します（設定の誤りなら、待っても直らないため）。途中で引き取られた接続でやり直しているときは、「並列数を下げる」ではなく、VPN と会社の証明書の確認（プロキシのサインインなら、パソコンのロックの解除も）と、最後のもう1周があることを示します。CLI がモデルの一覧を取れずにやり直しているときは、そのことを示し、通信エラーと同じ確認を勧めます。失敗の種類は、やり直すたびに runner がエラー全体（CLI のエラー出力を含む）から読んで記録したものを使います。失敗の案内には `cli-silent`（やり直し・接続の確認・待つ時間の延長、0 で見張りをやめる・一時停止）、`cli-intercepted`、`cli-gave-up` を足しました。
13. 無反応で止めたのと同時に Ctrl+C で実行を止めたときは、止めたこと（「Interrupted; …」）として記録し、やり直しも最後のもう1周もしません。

0.3.0ではVS Codeのサブエージェント方式（native）を削除しました。ワーカーは常にCopilot CLIで動きます。以下はすべてAIがチャットで提案し、同意を得て実行します。

1. `workerBackend: "native"`、`nativeHarness`、`nativeModelVerification`、`nativeInput` を含む設定は、移行方法を表示して停止します。`"workerBackend": "copilot-cli"` に直し、これらのキーを削除してから、judgeと翻訳の承認をやり直します。
2. コピー導入の案件に残る `.github/agents/migration-native-*.agent.md` は使われません。installerは削除しないので、AIが同意を得て削除します。
3. Copilot CLIが未導入、または未サインインの場合、AIが `npm install -g @github/copilot` と `copilot login` を実行します。利用者はブラウザでサインインを承認するだけです。
4. `migration/guardrails.json` は、AIが `guardrails show` を基に提案し、合意後に `guardrails install` で設置します。ホストが確認を求め、その許可が人間の設置行為になります。
5. 既存の設定には `fixPolicy`・`dependencyOrder`・`reviewFocus` を自動で追加しません。採用する場合は承認をやり直します。
6. `.github/copilot-instructions.md` の管理ブロックを短くしました（詳細はスキルにあります）。コピー導入で再インストールすると「Existing managed instructions differ」で止まるので、AIが同意を得て `<!-- code-migration-kit:start -->`〜`end` の間を新しい内容に置き換えます。ブロック外の利用者の記述は変えません。
7. ワーカーはセッションごとに動き（GitHubアカウントへの同期は利用者のCLI設定に従う）、IDを実行記録に残します。0.3.0より前のワーカーのセッションはIDが記録されていないため `sessions prune` の対象外です。GitHubアカウントに同期済みのものは、Copilot CLIの `/session` から整理してください。
8. ビルド修正の反復は、合意のうえで `build-loop` 1回の許可にまとめられます。

4. 既存の `migration/config.json`、RULEBOOK、inventory、manifest、移行したソースと記録は保持します。`verificationInputs` を設定し、必要なら `maxReviewInputBytes` を調整します。省略時はそれぞれ空配列、65536 bytesです。
   - 0.1.2ではmigration内のスクリプトと追加設定も追跡できます。state/results/gates/runs/run.lockをコマンドで直接指定したりverificationInputsへ登録していた場合は、スクリプト・設定を生成領域外へ移してください。
