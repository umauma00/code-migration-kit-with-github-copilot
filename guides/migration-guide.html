Who does what

登場するもの

AI は2か所で動きます。あなたが話すチャットの AI（オーケストレーター）と、キットのランナーが1件ずつ起動する作業用の AI（ワーカー）です。ランナー自体は AI を使いません。

YOU

あなた

チャットで質問に答え、承認などの確認ダイアログを許可します。コマンドは打ちません。

ORCHESTRATOR

オーケストレーター

Copilot CLI・Copilot app・VS Code のチャットで動く AI。アプリで選んだモデルで動きます。手順を読み、調べ、報告を書き、ランナーのコマンドを実行します。

RUNNER

ランナー（Node）

run_migration.mjs。AI は使いません。入力を固め、ワーカーを起動し、結果を検証してファイルに書き、ハッシュ付きの記録を残します。

WORKER

ワーカー

1回ごとに新しい copilot プロセス。担当（--agent）とモデル（--model）を固定し、指示ファイルは読ませず（--no-custom-instructions）、依頼は標準入力で渡します。JSON を1つ返すだけで、ファイルは書きません。

ワーカーの担当使えるツール役目
implementerなし（入力が上限を超えたときだけ読み取り）1ファイルを変換する
reviewer ×2なし（同上）動作とルール順守を、互いの結果を見ずに独立してレビューする
arbiter読み取りだけ（view・grep・glob）レビューの指摘を1件ずつ確かめ、本物か判定する
fixerなし（同上）確認された指摘だけを直す
surveyorなし準備工程で、範囲ごとにソースを読んで事実を表にする
preparation-auditorなし準備工程の成果物（比較器・依存・ルール一覧）を独立して監査する
オーケストレーター自身 ランナーが起動するワーカー AI なしの処理 人の確認

Phase 04, one file

04：1ファイルの処理

1ファイルにつき、ワーカーを3〜5回呼びます。どの呼び出しも新しい copilot プロセスで、前の呼び出しの会話は引き継ぎません。キットはレビュー担当2人に、同じ固定の入力（元ファイル、依存するファイル、RULEBOOK 全文、該当する inventory の行、変換結果）を渡します。

いつも1. 変換implementer が変換結果を JSON で返し、キットが変換先ファイルに書く
いつも（2つ同時）2. 独立レビュー ×2動作の担当とルール順守の担当が、互いの結果を見ずに欠陥を探す
指摘が1件でもあれば3. 裁定arbiter がすべての指摘をソースで確かめる。既定は「認めない」
認めた指摘があれば4. 修正fixer が認めた指摘だけ直す。既定（single-pass）では1回直したら完了とし、正しさはビルド・smoke・parity が判定
3指摘なし
変換1＋レビュー2
4指摘はあったが全部認めない
＋裁定1
5指摘を認めて直す
＋修正1
  • 修正後にもう一度レビューする設定（fixPolicy: rereview）では、直すたびにレビュー2が足され、その再レビューで指摘が出れば裁定1、認められれば修正1がさらに足されます。
  • レート制限や通信エラーは、待ってから同じ呼び出しをやり直します。やり直しも1回の呼び出しとして使用量に入ります。
  • 入力が上限（新規導入で 1 MiB）を超えるファイルだけ、ファイル一覧とハッシュを渡して読み取り専用で読ませ、その旨を記録します。

Worked example

100ファイルの例 推定

新規導入の既定値（同時4、修正は1回、型チェックなし、元のプログラムが動く）で、ワーカーを呼ぶ回数の目安です。つまみを動かすと 04 以降が変わります。準備工程は、範囲の数やまとまりの数で変わるため幅のある典型値を固定で使っています。オーケストレーター自身の会話は含みません。

ワーカー呼び出しの合計約 5321回ごとに Copilot CLI の呼び出し1回として、アカウントの GitHub AI Credits を使います。金額はモデルとトークン量で決まります。

前提：00b の監査なし（既存のテストを使う）、01 は同梱の解析器、02 は監査のまとまり3〜5、03 の試運転は10〜20ファイル、05 はファイルの約1割にビルドエラーが出て直す想定（1件あたり約4回）、05b・05c の修正はそれぞれ 05 の約4分の1・約4割。どれも案件によって大きく変わります。

Upstream

元のキット（Claude Code 版）との違い

元のキットは anthropics/code-migration-kit-with-claude-code（固定したコミット cf91c9d）です。移行の考え方と流れは同じで、変えたのは主に「AI の動かし方」と「承認・完了の確かめ方」です。

同じところ

  • 6つの段階（地図とルール → ルールの試験 → 全部変換 → コンパイル → 動かす → 動作を合わせる）
  • ルールブック（RULEBOOK）と一覧（inventory）を先に固め、変換中は書き換えない
  • 比較器を先に作り、わざと壊した実装を見抜けるか確かめる
  • 2人の独立レビューと、既定で「認めない」裁定役
  • 03 の比較 A/B・差分の検査・試運転、依存関係は決まった手順のスクリプトで作る
  • 同じ種類の失敗が3回出たらルールの問題として扱う、不明な所は最も保守的に訳して TODO(port) を残す
  • 付属の題材（examples）・RUN-NOTES・依存解析のテスト題材の一部は元のまま

このキットが足したもの

  • 初期設定の質問と run-settings.json（設定をあとで一括で変える・別のセッションで再開する）
  • 元のプログラムが動かない案件の方式（source-only）と、仕様もない案件の方式（source-as-spec）
  • 準備工程で全ファイルを範囲ごとにワーカーへ分ける調査（survey）と、準備工程の独立監査の約束事（修正は1回）
  • 03 の試運転をプロジェクトの外で、専用の許可を取って行う仕組み（pilot）
  • ビルドエラーを読み取ってレビュー付きで直す繰り返し（build-loop）と、smoke・parity の失敗の修正の列
  • 依存解析器の対応言語の追加（C#・Java・VB.NET・PHP・COBOL）と、自作の解析器の作り方
  • ワーカーの使用量の記録（usage）と、ワーカーの会話記録の確認・削除（sessions）
  • Windows を主な環境とした対応と、Windows・Ubuntu での自動テスト

元から外した・変えたもの

  • 元の skill フォルダーは、オーケストレーター専用の手順（skills/code-migration）に書き直し、スラッシュメニューには出さない
  • 元の README と CLAUDE.md は docs/UPSTREAM-README.md・docs/UPSTREAM-CLAUDE.md にそのまま残し、いまの規則は docs/OPERATING-MANUAL.md
  • 元の build_daemon.sh は残したが、主な手段はランナーの build・build-loop。queue_runner.mjs は「レビュー済みの記録」で数える形に書き直した
